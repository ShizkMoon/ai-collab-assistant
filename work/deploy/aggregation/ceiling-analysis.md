# 三出口 900 Mbps：现有上限、证据与最小判据

当前记录中的 `ifb-cake` 为 **650 Mbit**。如果目标下载实际经过这个队列，持续应用吞吐 900 Mbps 在该配置下不可能。三个逻辑出口仍共享一根千兆 WAN；900 Mbps 接近这根链路的大包 TCP 有效容量，需要先移除试验中的 650 上限并验证实际路径，再判断是否还有容量。本支线只读已有文件，没有网络搜索、SSH、测速或设备修改；设备之后发生的变更以主线新读回为准。

## 硬边界与计算口径

| 层 | 可得出的边界 | 不能得出的结论 |
| --- | --- | --- |
| 物理 WAN | 文档记录一根千兆链路，`wan`、`eswan2`、`eswan3` 共用它；三个账号／接口不产生三根千兆线的容量 | 不能把逻辑接口的计数相加成为物理吞吐，也不能认定每路固定 300 Mbps |
| 千兆以太网、MTU 1500 | 在无 VLAN、IPv4、完整大包、无重传等理想条件下，线速上界约为 `1000 × 1460 / 1538 = 949.3 Mbps`；常见 12 字节 TCP 选项后约 `1000 × 1448 / 1538 = 941.5 Mbps`。TLS、代理封装、小包及重传会继续降低应用字节比例 | 这是条件计算，不是本机持续测速；接口 sysfs 字节通常不含全部线上的前导码／帧间隙，不能把其 1,000 Mbps 当作唯一线速判断 |
| 下载 CAKE 650 Mbit | 记录为 overhead 38、MTU 最大 1500。上述条件下应用上界约 `650 × 1460 / 1538 = 617.0 Mbps`，带 TCP 选项约 `612.0 Mbps`；代理和 TLS 再占开销。短暂突发、计时误差或绕过 IFB 不能算突破整形上限 | 650 不是应用净速率，也不是每个账号各 650；增加连接数不能使经过此公共队列的持续净下载达到 900 |
| Wi-Fi LAN | 默认 AQL 完整 1 GiB 的两组记录为 886.32／868.70 Mbps；缩短 AQL 的两组为 975.06／838.09 Mbps，未复现收益，已恢复默认。说明当前位置 LAN 曾接近或超过 900，但默认记录没有稳定超过 900 | 不能用 2,402 Mbps PHY 或一次 975.06 宣称端到端稳定 900；RAM→Wi-Fi 不经过校园 WAN、UA3F、完整 OpenClash 路径 |

900 Mbps 的应用字节等于 112.5 MB/s，约 107.3 MiB/s。在上述千兆大包模型中，要承载它约需 948～956 Mbps 线速，还没有计入 TLS、额外封装及重传。物理层没有直接排除这个目标，但余量已经很小。

证据：[当前运行队列](../next/current-runtime-socket.json)、[队列应用及实际 1500／1538 计数](../next/cake-applied.json)、[调研正文的拓扑与无线实测](../../../outputs/ax6000-mainline/路由器调优与校园网方案调研.md)、[使用说明](../../../outputs/ax6000-mainline/使用说明.md)。

## 当前瓶颈证据的强弱

1. **650 是已知配置上限，实际大下载覆盖仍须读回。** 三路小请求进入 IFB 已有证据；历史大下载的同源外层 ESTABLISHED 覆盖不足。不能仅凭 `ifb-cake` 存在就认定每个目标业务已被整形。主线应把本次下载的物理 WAN、IFB 字节与实际外连对应起来。
2. **CPU 存在候选信号，未确认成特定进程瓶颈。** `cake-comparison.json` 中开 split-gso 完整批次 263.80 Mbps，17 个稳态观测区间，连续 14 个区间有任一核心 busy ≥90%，最高 94.4%。关闭样本 232.81 Mbps，24 个区间，连续高占用只有 1 个。两组均因实际外连覆盖不足而 `inconclusive`，且不是随机交替对照。这里的“任一核心”可能随区间变化，不能写成同一核连续 14 秒满载，也不能确认 CAKE 导致 CPU 饱和。no-split-gso 样本不完整，已恢复 split-gso，不能把它作为收益方案。
3. **增加连接的成本已经可见。** 此前完整 PC 路径 16→32 连接，吞吐 557.61→574.07 Mbps，仅约 +2.95%；整机 busy 58.1%→70.0%，softirq 20.7%→25.1%。UA3F／clash 的进程 CPU 以四核总量为分母，各约 7.76／7.47%→9.56／9.78%；25% 才相当于一核满载。这是历史各一次批次，不证明现在固定卡在 CPU，更不证明 Ninja 加密或 Go 用户态锁。
4. **账号限速值、三路独立配额尚无直接证据。** 三个认证在线、不同账号第三路成功与小请求可达，均不等于三份可叠加的固定额度。历史裸双出口 617.54 Mbps 只证明当时该同源批次的双出口传输与容量，不能外推三路 900。
5. **源站／源 IP 的限制仍未排除。** 旧 USTC 同源测试出现 HTTP 429，全部 case 均未完整，必须排除。源站的每连接、每源 IP 或总服务容量都可能形成平台；单一源的低速不能直接归因校园账号。
6. **全局重传／内存计数不能定位损耗。** `diagnose_download_overhead.py` 的 `/proc/net/snmp`、`netstat` 和 softnet 增量包含背景业务及多条 TCP leg；内层和外层可能重复体现同一应用字节。不能把 WAN／应用字节比、TCPRetransSegs 或 memory pressure 全部算成无线丢包、账号限速或源站损失。旧 `tcp_mem` 扩大对照已有负收益并恢复，不因这些计数重复扩大内存。

证据：[CAKE 有限对照](../next/cake-comparison.json)、[既有并发分析](../ninja/download-throughput-next-probes.md)、[裸双出口完整批次](../microsoft-throughput-both-direct-1gib.json)、[429 无效批次](../wan-throughput-same-source.json)、[计数采集脚本](../../../docs/local-only-materials.md)。

## 主线可以直接实施的最小实验

先读回当前链路协商／MTU、队列、认证 PID 与 MWAN，再做下面的自适应分层。每次只运行一组负载，不同时跑 LAN 测试和公网测试。每组使用同一可 Range 的大文件、同一固定目的 IPv4、HTTP/1.1 独立连接、相同完整字节范围；每条退出码、206 和精确字节均须通过。直接绑定出口的请求沿用已验证的 source IP／device／mark 绕过代理方法，不能只填写一个接口名称后假定成功。

建议最小完整负载为 **12 × 192 MiB，共 2.25 GiB**：裸三出口每路明确 4 条，UA3F／PC 路径保持相同 12 条。若达到 900 Mbps，完整批次约 21.5 秒，去掉头尾仍可有至少 10 秒稳态窗。1 GiB 在 900 Mbps 只需约 9.5 秒，不能同时提供 10 秒稳态。可以沿用现有请求时限和健康停止条件，429、认证变化、返回字节不完整、业务失败或观测缺口时停止该轮。

| 顺序 | 对照 | 需要回答的问题 | 最小可执行判据 |
| --- | --- | --- | --- |
| 1 | 当前完整 PC 路径，CAKE 650；随后仅暂时撤销自有整形的同组 PC 路径；必要时恢复 650 再测 | 650 或 CAKE 处理是否在限制目标？ | 同窗证明目标流经过 IFB；650 组在约 612～617 Mbps 应用平台、关闭后越过平台且恢复组重现，才支持整形限速。若两组都远低于此值，650 的数字上限尚未成为实际吞吐瓶颈；CPU／队列成本仍另判。临时试验须避免 watcher 立即重建队列，结束恢复原服务、队列与启用状态，不能靠反复删 qdisc 和 watcher 竞争 |
| 2 | 同一临时无整形窗口：路由器本机，三个出口各绑 4 条直接下载 | 校园路径／源站／账号总容量是否先到上限？ | 三路对应外层 ESTABLISHED、正确源 IP 和 mark 同时存在并有接收字节；总应用速率按全批完成时间计算。若此组已达 900，线路／该源／该窗容量条件成立，可继续定位完整 PC 路径；若低于 900 且 CPU 有余量，先进入源／额度区分，不把低速归因 UA3F |
| 3 | 同一窗口：本机 curl→现有 loopback SOCKS→UA3F→三出口 | UA3F 及额外 TCP 转接是否付出明显成本？ | 与裸三出口保持相同源、总字节、并发与队列状态；读回实际 UA3F 新外连和三路字节。若裸三路快、此层显著降低且 UA3F／system／softirq 或特定线程持续高占用，缩小到 UA3F／内核收发路径；仍不能直接命名某个锁或加密算法 |
| 4 | 同一窗口：PC→OpenClash→UA3F→三出口 | 剩余成本是否在 OpenClash、Wi-Fi 或 PC？ | 本机 UA3F 接近裸三路而 PC 明显低时，才进入本层；用临近的 RAM→PC LAN 完整样本核对无线当时容量。LAN 自身达不到 900 时不能把该 PC 公网未达 900 当作账号上限；LAN 足够只排除明显 LAN 容量不足，不能排除并行转发时的 CPU 竞争 |

为了少跑负载，可以先用已有 650 样本作导航，**先完成第 2 项**；只有裸三出口确有足够容量，再实施第 3／4 项和必要的 650 回读对照。旧样本不能代替同轮因果对照。表中顺序是问题关系，不要求无条件做完全部格子；确认硬上限后应停止无用分支。

最低观测集：每秒物理 WAN RX、`eswan2/3` RX、各 CPU 的 busy／softirq、UA3F／clash 进程 jiffies；负载开始／中间／结束取得 qdisc 字节与 drop／mark／backlog；筛选固定目的 IP 的 UA3F socket inode→`/proc/net/tcp*`→conntrack 外层源 IP／mark。纯内层 PC curl 的 local_port 不能直接与被代理重新建连的外层 source_port 相等匹配。物理 `wan` 已覆盖底层总量，**不再加上 macvlan**；减去 macvlan 得到的 main 只是同窗背景可控条件下的估计，不能单凭它确认应用连接归属。

## 一次结果如何分类

- **线路容量候选**：多个来源或足够连接下均接近千兆大包有效上限，物理线速估计接近上限、CPU 有余量，队列／包丢失没有另一个更低平台。一次 900 仅证明该窗成功。
- **账号／出口容量候选**：无整形、CPU 有余量；三个绑定出口分别单独与同时测试，结合第二个独立且可正常 206 的来源，每路平台可复现。若一号账号的两出口同时总量接近它们单独的单路平台，而另一个账号加入使总量增加，才支持共享账号额度的假设。服务器对校园源 IP 的限制仍可能等价呈现，严格套餐结论仍需规则或更强证据。
- **CPU 路径候选**：增加并发吞吐平台不提高而一个或多个 CPU 连续高占用，UA3F／clash／softirq 的增量与路径切换相符，降低负载后恢复。仅整机平均未满或一个 94.4% 峰值都不足。按既有安全门槛，连续 3 个观测达到单核 95% 可停止压力，不必追求把机器压死。
- **源站／单源限速候选**：固定路径与参数下更换独立源后平台显著变化、单源 429 或其并发增长不增加总量；保留来源差异，不能把两源相加的速度写成同文件下载速度。
- **900 Mbps 验收**：全批完整净字节／完整墙钟时间达到 900，至少 10 秒稳态、真实三路外层连接与字节覆盖、认证／TTL／业务健康保持，且紧邻重复一次。只有稳态峰值达到时写“稳态短窗峰值”，只有一次完整批次达到时写“一次完整批次”；即使两次通过也不写数日稳定或所有下载源可持续。

现有 `wan_throughput_probe.py/.sh` 与 `microsoft_throughput.py` 的裸 `both` 分支只覆盖 `wan/wan2`，旧接口统计也只有 `wan/eswan2`；不能不改读取范围就拿来验收三路。旧 USTC 同源脚本把两个逻辑 stream 指向同一镜像，并遇到 429，不能作为 900 目标的可靠基线。主线可复用其绑定与完整性方法，三出口适配及实际设备操作由主线单独负责。
