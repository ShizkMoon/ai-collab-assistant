# 三路聚合：最小同源对照与 900 Mbps 验收

目前已有“三路均能承载真实请求”的证据，尚不能据此判断三路相对单路或双路的速度增益，也没有稳定 900 Mbps 的证据。最新 `next/cake-comparison.json` 的同源短样本是关闭队列约 232.81 Mbps、开启 split-gso CAKE 约 263.80 Mbps，另一个 no-split-gso 样本不完整；这些数值不是单、双、三路的同期对照。旧 581 Mbps 等样本也不能代替当前对照。

本轮应先做有边界的容量筛查，再核对 PC 实际链路。测试期间由根代理临时停用下载 CAKE，并在 finally 和独立回退定时器中恢复当前 `650Mbit` 下载、上传 unlimited 配置。不改认证、常用流量策略或永久限速。当前 650 Mbit 下载整形上限本身不能用于验收 900 Mbps。

## 已有脚本的可用部分与错误边界

- `root/microsoft_throughput.py` 可以复用同一 Microsoft 对象、IPv4 固定地址、HTTP/1.1、Range、Connection: close、无重试、丢弃负载，以及自有 router curl 的设备 / 源地址绑定。但它的 router both 模式固定每路 4 条：单路 4 条、双路 8 条会同时改变总并发，须改成固定总数；也只统计 wan / eswan2，尚不覆盖第三路。
- `root/frontier_small_flow.py` 可以复用 UA3F PID → `/proc/PID/fd` socket inode → `/proc/net/tcp` ESTABLISHED 四元组 → conntrack original / reply → SNAT 地址与 WAN 地址的对应。该脚本自己已经限定：观察到的 outer socket 不等于已逐条映射到某个 curl。
- `frontier/queue_baseline.py` 和 `next/queue_cake.py` 的 coverage 将 PC `curl.local_port` 与 outer conntrack 的 original sport 比较。OpenClash → UA3F 重建连接后，这个端口通常改变，不能继续作为覆盖条件。应替换为外层所有权与四元组对应，不能直接删除过滤后把全部同源背景流量算入测速。
- `root/summarize_download_flows.py` 的“基线没有出现的新四元组”可以辅助排除旧连接；其 mark 计数和接口总字节不是完整的逐请求归属证据。物理 wan 包含 macvlan，不能把 wan、eswan2、eswan3 接收字节直接相加。

## 选择控制哪一层

最快、可严格限定自有流量的第一层对照是路由器自有 curl socket：复用已验证的 libwrap_mwan3 设备 / 源 IP 绑定，只对本次新建 curl 生效。第一条慢速 Range 预检必须读回 curl 的真实 Internet socket、conntrack 和指定出口。如果 curl 被透明代理重建、实际 Internet outer socket 属于 UA3F，则这项绑定不再证明最终出口，不得继续称为受控通道容量测试。

router curl 路径通过预检时，用相同源站、相同 IPv4、相同 Range 列表和固定总并发 12 条比较：单路 12 条；双路每路 6 条；三路每路 4 条。通过可控源地址及真实 conntrack 确认出口，不更改 MWAN 权重、不禁用其他账号、不重启 UA3F。它回答的是通道与共享链路能否聚合，不能证明 PC 经过 OpenClash → UA3F 后具有相同速度。

第二层保留 PC 当前实际链路。最小可立即执行的测试是三路策略原样运行，按下面的方法捕获 outer socket 并计算实际 PC payload。与第一层结果比较，可以定位“容量足够但 PC 路径受限”，但不能直接将跨路径差值解释成聚合增益。

若必须完成 PC 同路径的一 / 二 / 三路严格对照，推荐控制自有测速连接的存续，而不写全局路由规则：测试器逐条打开 HTTP/1.1 Range 请求，暂缓读取响应正文，读取前后两次 UA3F fd / TCP / conntrack 快照；只有新增 outer 四元组唯一且与当前请求一一对应时，才给这条自有请求登记出口。保留所需出口上的请求，关闭本测试器不需要的请求；凑齐固定 12 条后统一开始读取负载。单路保留同一出口的 12 条，双路各 6 条，三路各 4 条。募集最多 36 次或 20 秒；达不到目标分配就报告“不具备该组受控对照”，不修改共享策略补齐。

门控期间代理和内核可能预读，正式统计应剔除统一启动后的前 3 秒，并记录募集阶段接收字节。若代理复用连接、一次请求产生多个 outer、出现其他同源新请求、inode 生命周期不清楚或 outer 在暂停期间关闭，则一一映射不成立，应停止这组，不靠时间邻近猜归属。不能把此方案直接套进现有 curl 结果端口匹配：它需要一个能够控制 HTTP 响应读入的自有测试器。

不要用 PC 原端口的 skb mark 期待它自动跨越代理；不要事后给已建立 outer conntrack 换路；不要按整个 UA3F UID/PID 强制所有流量；不要仅用 Microsoft IP / 80 的全局 OUTPUT 规则，因为那也可能改变后台更新等非测速流量。以上做法都不满足“只影响自有测速流”。

## 最小测试顺序

1. 同源 1 KiB / 小 Range 预检：确认 HTTP 206、精确 Content-Range、对象总长度、固定远端 IPv4、无重定向与代理缓存改变；读取三路当前地址、路由及认证 / UA3F / Clash PID。沿用现有对象，其旧证据总长为 6,326,574,815 字节，但正式测试必须重新读回，Range 不能越界。
2. 记录空闲 5 秒；暂时停下载 CAKE，读回队列；固定总并发、文件区间、总字节与 CPU 观察方式。第一次先选择现有表现最好的单路、该单路加第二路、三路；末尾再测相同单路，即 `A1 → A2 → A3 → A1`。每组最多 768 MiB、最多 60 秒，完整 Range 结束后留 3 秒恢复观察。这个规模用于初筛，900 Mbps 时约 7 秒，不能称为稳定 900 验收。
3. 若后一个 A1 与前一个 A1 偏差超过 15%、源站 IP /对象 / 协议变化、测试失败或三路未实际覆盖，则报告时间 / 源站条件不稳，不强行计算确定的聚合收益。若结果接近测量波动，只做一次有针对性的重复，不无限增加 benchmark。
4. 测 PC 当前三路实际链路，保留同样总并发和同源对象；按 outer inode 证据核对分配，记录 PC payload、Wi-Fi / Ethernet 和 CPU。若需要用户路径的严格因果结论，再执行上述 PC 连接募集对照。
5. 全部结束或任何异常时，只结束自有测试进程，恢复当前队列，读回配置、认证 PID、DNS、国内及代理 HTTPS；不清空全部 conntrack。

同并发 A1 / A2 / A3 是最小增益测试，并非每一路完整性能审计。若要判断第三路为何无益，再追加第三路单独测试；若某个单路异常，先排除该路再解释三路结果。

## 外层连接取证与吞吐计算

每组开始前、募集期间和负载中每秒读取：UA3F / Clash PID、UA3F fd inode、`/proc/net/tcp`，以及只针对固定远端 IPv4 / TCP 80 的 conntrack。记录稳定的请求 ID、PC 测试进程、outer inode、outer original 四元组、conntrack reply 四元组、ct mark、映射出口、出生 / 最后观察时间及接收字节变化。ESTABLISHED 的 UA3F inode 是进程所有权证据；reply dst 对应当前 WAN 地址是 SNAT 出口证据；mark 和接口计数是交叉核对。

预先保存同源已存在的 outer；存在非测速同源流量时，不能把全体同源计数作为本次负载。如果无法逐请求映射，PC 三路测试只能报告“UA3F 同源新外层连接及出口参与，个别请求映射未完成”。同源 1 KiB 延迟探针应分开记账，不能当作下载流覆盖。

有效负载速率使用所有自有测速请求接收到的正文总字节除以同一单调时钟的公共负载窗口，再乘 8 / 10^6。禁止相加每条 curl 的平均速度，禁止把累计历史 conntrack 字节当成本轮增量，禁止相加物理 wan 与其 macvlan 字节。完整 Range 要核对精确字节；中途停止的请求必须标成不完整，只有直接计数并带时间戳的已读正文可用于固定时间窗口吞吐。

## 必须同步观察的限制

- 每核 CPU busy / softirq 的 1 秒增量，UA3F、Clash 和测试 curl 的进程 / 线程 CPU；持续单核 90% 以上且速率不再增长提示处理路径瓶颈。整机平均 CPU 低不能排除单线程上限。读回 TCP 重传、softnet drop / time_squeeze、MemAvailable 和代理 PID 变化。
- 物理 WAN 速率与双向协商，PC Ethernet 协商；若使用 Wi-Fi，记录频段、信道宽度、协商速率、信号和本次设备。Wi-Fi PHY 数字不是有效 payload 速率。为了判断稳定 900，应优先使用已确认的千兆或更快 Ethernet；若不具备，就如实报告当前 Wi-Fi 路径结果。
- 三路有各自的实际 outer 流量和持续正文，而不是只有三个心跳或 204 请求。三路共用同一物理口、交换网络或校园账号策略，三份地址不代表三份独立带宽。HTTP 明文源站容量也不能代表香港代理节点的能力。

## 如何判定聚合有用及稳定 900

受控同路径、固定总并发的 A2 / A3 相对 A1 提升超过夹在前后的 A1 波动，且新增通道承载显著下载字节，才可以报告本次源站下的聚合增益。若 A3 与 A2 相当，第三路在这个样本没有可测吞吐收益；它仍可能有容错作用，但本测试没有测容错。若自有 router curl 达到高速度而 PC 实际路径低得多，应优先查 PC 链路、OpenClash / UA3F 单线程或代理处理，不能继续通过增加账号推断能到 900。

稳定 900 Mbps 单独验收：在最终采用的实际 PC 路径上，每轮至少 3 秒预热加 30 秒持续正文窗口，按 1 秒采样并计算三个连续 10 秒窗口。每个 10 秒窗口及整段 30 秒的有效 payload 都达到 900 Mbps，且三次独立完成的轮次均满足、无业务中断 / PID 重启 / 明显累积丢包，才报告“本次源站、该连接方式、这些时间窗口下稳定达到 900 Mbps”。单次峰值、总接口吞吐或小于 10 秒的传输不算稳定。该定义不证明所有源站或全天可达。

只有初筛接近或达到目标时才进入这个阶段。每轮设约 4 GiB 正文与 45 秒的上限，三轮最多约 12 GiB；如果初筛显著低于目标，直接交付瓶颈证据和下一步，不用增加流量证明同一失败。恢复 650Mbit CAKE 后应明确日常配置受该上限限制，不能把临时停队列的 900 Mbps 结果称为当前配置持续速度。

本文件是方案；本代理只读了指定脚本和现有证据，没有执行 SSH、测速、浏览器 / 设备操作或修改任何生产设置。
