## 0. 一句话

单会话 Agent 的上限是模型能力，多任务的上限是人的注意力。Super-agent 把"会话"从产品形态降为系统实现细节：常驻 Router 承接全局连续性与分派，隔离的 Worker 并发执行，事件而非提示词驱动，计算/状态/环境三者解耦，外部 Watchdog 兜底自愈。

## 1. 四个特征

| 特征 | 含义 | 反例（单 ReAct Loop） |
|---|---|---|
| 连续 | 用户在 IM / GitHub 评论等熟悉界面交互，感觉只有一个 Agent | 换会话就丢上下文 |
| 高效 | 并行推进多个复杂任务，不必等上一条命令完成 | 同步阻塞，一问一答 |
| 主动 | 持续观察环境事件，值得做就推进，不需要时保持安静 | 只响应键入的提示词 |
| 持久 | 始终在线，接入真实工作环境，异常自动恢复 | 本机关机即停 |

单 Session 的结构性问题：一个人通常只能同时跟进 3–5 个活跃会话；多任务吞吐被人力切分。

## 2. 双层架构

**权衡**：所有事件进同一 Session → 上下文最连续，但串行、吞吐低、多任务细节混杂；每条事件新开 Session → 吞吐最高，但缺全局上下文、多方各自回复造成混乱。

| 层 | 职责 | 关键约束 | 模型选择 |
|---|---|---|---|
| Router（常驻） | 承接全部人类交互、跨任务协调、全局记忆、充当序点（Sequence Point） | **不执行具体任务**，甚至不配 Bash；只做交互与分派 | 轻量模型即可 |
| Worker（隔离） | 单任务执行，挂完整工具 | 不直接对人说话，向 Router 汇报；同层 Worker 之间通常不直接通信 | 最强模型 |

- Session 只应作为系统实现细节，不应作为用户的认知负担；让用户手动管会话是 LLM API 时代的设计惯性。
- Router 不是吞吐瓶颈的证据：上一轮推理期间到达的事件会积压，下一轮合并注入，形成 **batching**。Prefill 并行计算使单次请求耗时增长远慢于 batch 增长，因此"积压越多，单个决定分摊推理时间越低"，上限是上下文长度。
- 扩规模时 Router 内部可多层过滤或水平分片（Sharding），代价是记忆连续性下降。

## 3. 事件驱动

驱动源从人类提示词变为环境中的半结构化事件，称 **Trigger**：群聊消息、邮件、日程提醒、代码评审评论、CI 结果。

### 3.1 两级过滤（Fast / Slow Path）

真实事件流"高噪音、低触发率"。对每条事件都调大模型不可承受，因此：

- **程序层（Fast Path）**：来源、群组范围、用户/机器人白名单等确定性条件，代码直接准入；按来源分别设"仅响应明确请求""作为候选""直接忽略"。
- **语义层（Slow Path）**：模型按提示词判断是否需要行动；同时是面向人的自然语言扩展点，可随时开关或新增策略。

### 3.2 Thread 与订阅直通

**Thread**：同一 PR、同一 IM 话题、同一邮件串下的连续 Trigger 构成一条事件流。

- **未订阅（Slow Path）**：Router 观测全部事件，但只处理冷启动与分派。
- **已订阅（Fast Path）**：Router 为某 Thread 建 Worker 后，该 Worker 直接订阅；后续事件由程序直通 Worker，**不经 Router**。超出范围时 Worker 可退订或交回 Router。
- 订阅是**多对多**：一个 Worker 订阅多个 Thread，一个 Thread 可被多个 Worker 订阅；多个 Worker 在同一 Thread 上收到相同事件，因而有机会自行发现并解决冲突，无需点对点通信。
- 输出侧仍收口：Worker 把关键结论报给 Router，由 Router 统一回复并同步全局记忆。

### 3.3 上下文组织：Inline & Spill 与链式召回

把上下文窗口当缓存管理：

- **Inline**：近期很可能用到的信息直接内联，省去工具往返。
- **Spill**：超预算或低频内容留在窗口外，只留引用/摘要，按需读取。
- 渐进顺序：先给 ID + 摘要 → 利用局部性附上紧密关联对象 ID → 附时空相邻内容（前 50 字、前后消息、相邻评论）→ 超上限截断并保留续读入口。
- **链式召回（Chain of Recall）**：Trigger / Thread / Worker Session 都有唯一 ID，注入时内联下一跳对象的 ID，构成引用图；模型可逐跳展开（当前消息 → Thread → 相关 Worker → 该 Worker 关联的另一评审 Thread）。缓解 Router 长程丢上下文。

### 3.4 投机执行（Speculative Execution）

结果不确定时先消耗后台算力尝试，有价值就交付，没价值就丢弃。

- 个人场景：收到会议邀约 → 后台核对日程冲突、搜集背景、备好草稿 → 用户过目后直接确认。
- 研发场景：群内有人反馈问题 → 先静默复现并尝试修复，确认且修复简单才交付，否则保持安静。

## 4. 面向人的交互

### 4.1 全双工（异步 ReAct Loop）

经典循环里 `run()` 同步阻塞，工具执行期间无法接收新输入。改造为：

- 耗时调用改为 `start()` / `stop()`，`start()` 立即返回 **Started** 通知，循环不等待。
- 后台完成后，结果作为**一条新事件**投递进会话。
- 模型可调 `stop()` 终止过长的后台命令。
- 效果：前台响应与后台执行解耦；新输入在当前推理步结束后即被处理。

### 4.2 多信道

| 信道 | 规范 |
|---|---|
| IM | 低打扰；只在需要决策/验收时通知；只问直接问题、给短结论。硬规定：单次回复不超过 100 词 |
| GitHub / 邮件 / 文档 | 结构化、高密度异步交付：问题背景、改动说明、验证结果 |

冗长推理与密集工具调用被隔离在 Worker 内，不直接输出到外部信道。

## 5. 计算、状态与环境的分离

本地 Agent 把 Agent Loop、会话状态、执行环境绑在同一台机器：休眠即停，且访问不到其他设备。

1. **计算与状态分离**：Loop 放进无状态弹性容器，Session 状态进数据库；容器可重启/替换/水平扩展，连续性由存储保障。
2. **计算与执行环境分离**：不把环境搬上云（未提交修改、私有凭据、内网依赖、特定硬件难以同步），而是在端侧只放**不保存会话状态的轻量 daemon**，只负责执行命令与返回结果。Agent 按需读取环境中的上下文。
   - 与 Anthropic 的"脑手分离"同向，区别在场景：那边是托管沙箱与客户 VPC，这边是用户日常、**可能间歇在线**的个人机器。
   - 支持 BYOM（Bring Your Own Machine）：个人电脑、托管机、按需创建的算力都能接入；设备重新上线后可由云端 Agent 触发补做任务。

## 6. Watchdog

长期运行的分布式系统不能只靠主系统内部逻辑保证可靠，需要**外部**控制回路（Control Loop）。

- 主系统外置一个独立 Watchdog Session，用定时消息驱动。
- 不止看进程存活：**判断 Worker 是否有实质进展、方向是否偏离目标**——模型无效循环不是崩溃，存活探测发现不了。
- 异常时介入修复；外部偶发故障则持续复查至恢复。
- Watchdog 本身是完整工具能力的 Session，维护者可用自然语言问它故障原因，也可让它在线修正主系统行为（增删提示词、调整触发规则）。

## 7. 初步实验（合成负载）

| 项 | 结果 |
|---|---|
| 负载 | 群聊 + GitHub CI 消息流，单次约 300 条消息，其中约 20 条工作请求；5 次重复 |
| 端到端完成时间 | Super-agent p50 **12.4 min** / p95 **15.7 min** |
| 单 Session + Subagent（中性提示） | 5 次中 **0 次**委派，全在主 Session 被新消息打断，p95 **29.5 min** |
| 单 Session（提示优先委派） | 5 次中 4 次委派，仍慢于双层，第 5 次判断"工作很小"自己执行，形成长尾 |
| 代价 | Super-agent 读缓存 token 高于单 Session——用 token 换更短更稳的完成时间 |
| 去掉直通 | 完成时间基本不变，但 Router 决定数 **+30%**，总读缓存 token 23.23M → 31.77M（**+37%**） |
| Router 批处理 | 到达速率 1→40 条/分：平均 batch 1.0→2.8，单次请求 2.5→3.9 s，单个决定分摊 **6.4→1.6 s** |

结论：分工靠架构而非提示词——提示词方案在"这活儿很小"的判断上不稳定；直通不提升质量，但为 Router 省下可观 token 与推理；当前团队规模无需过早分片。

## 8. 开放问题

1. **扩展双层架构**：Router 何时分片、粒度；Worker 间何时需要直接通信；Router 专项训练（事件判别、批量分派、上下文召回）；**跨月以上的长程记忆**。
2. **脱离 Session 后的人机协作**：以聊天窗口为中心是路径依赖；交互可更多发生在领域特化界面；底层一个会话可能对应多个 Session；中途干预/接管/实时协同的产品形态未定。
3. **上下文边界与 A2A**：组织按"共享/隔离"划边界配实例；跨实例（个人助手 ↔ 团队实例）的 A2A 通信与权限边界未解。
4. **安全与隐私**（对本仓最相关）：
   - 事件驱动扩大了不可信输入面（提示词注入）。
   - 云端 Loop 若被攻破，其连接的全部端侧 daemon 都可能被控制。
   - 即便未被攻破，**凭据一旦进入模型上下文就可能在正常执行中泄露**；需要让 Agent 不接触凭据本身而使用凭据。

## 9. 与本仓的对照

| 文章模块 | 本仓对应 | 处理 |
|---|---|---|
| 双层 Router / Worker | [系统拓扑](system-topology.md) 的入口 / 编排 / worker | 采纳职责划分；Router 明确为 DS-Bot（无 shell），Worker 为 Orca 会话 |
| Trigger 两级过滤 | [架构总览 §7](architecture.md) 判定前的过滤层 | 采纳；但语义层只产出**候选**，不直接授权动作 |
| Thread + 订阅直通 | 新增 `thread_id` / `subscriber` 字段 | 采纳；直通绕过判定，但落定与记账不变 |
| Inline & Spill + 链式召回 | 简报装配、记录召回 | 采纳为简报构造规则 |
| 投机执行 | 新增 `spec` 处置类 | 采纳；限定在只读动作与草稿类产出 |
| 全双工 | 处置不阻塞新事件 | 采纳 |
| 多信道输出规范 | [架构总览 §9](architecture.md) 呈现面 | 采纳 IM 短、异步信道结构化的分工 |
| 存算 / 环境分离 | 工作站（算+账）/ 入口宿主（无状态）/ 设备（daemon） | **变体**：单用户自托管，账仍在工作站，不上云 |
| Watchdog | 新增外部控制回路一节 | 采纳监控"进展与偏离"；**不采纳**在线改规则 |
| Watchdog 在线修正规则 | — | 不采纳：与本仓不变量 5（规则改动由人确认）冲突 |
| 多实例 / A2A / 分片 | — | 不适用：单用户单实例 |
| Session 作为实现细节 | 与"用户不感知会话"一致 | 采纳为产品原则：入口侧只讲任务与事件，不讲 Session |

两条需要说明的取舍：

- **本仓多了"账"**。文章以会话历史 + 数据库状态为主；本仓是事件先入账、账为唯一事实源。原因不同：文章面向团队研发协作，可靠性由 CI/PR 兜底；本仓跨度到日常生活，需要"没人在场时发生的事"也能事后追溯。
- **本仓的判定更保守**。文章允许 Watchdog 在线改触发规则与提示词，那是给内部团队用的；本仓按不变量 5 保留人工确认，代价是规则迭代慢一些，换来的是出错时能回答"谁改的、为什么"。
