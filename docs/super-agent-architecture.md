## 0. 核心观点摘要

单会话 Agent 的能力上限取决于基础模型，而多任务并行的上限往往受限于人的注意力。Super-agent 架构将"会话（Session）"从面向用户的交互形态下沉为系统内部实现细节：由常驻 Router 维护全局上下文并负责任务派发，由相互隔离的 Worker 并发执行具体任务，以环境事件（Trigger）替代人工提示词作为主要驱动源，将计算、状态与执行环境三者解耦，并配合外部看门狗（Watchdog）实现异常自愈。

## 1. 四个核心特征

| 特征 | 含义 | 单会话 ReAct 循环的局限 |
|---|---|---|
| **连续性** | 用户在 IM、GitHub 评论等日常界面直接交互，体感上面对的是同一个持续在线的 Agent | 切换会话即丢失历史上下文 |
| **高吞吐** | 后台并行推进多个复杂任务，无需等待上一条命令执行完毕 | 前台同步阻塞，只能一问一答 |
| **主动性** | 持续监听外部环境事件，满足条件即自动推进，无需打扰时保持静默 | 仅被动响应用户手动输入的提示词 |
| **持久性** | 服务常驻运行并接入真实工作环境，遇到异常可自动恢复 | 本地终端关闭或电脑休眠即中断 |

## 2. Router / Worker 双层架构

将所有事件塞入单一 Session 会导致串行阻塞与多任务上下文互相污染；而为每条事件完全独立地新建 Session 又会丢失全局上下文并导致多方各自回复。双层架构对此做了职责切分：

| 层级 | 核心职责 | 约束边界 | 适用模型规模 |
|---|---|---|---|
| **Router（常驻）** | 承接全部用户交互、跨任务协调、维护全局记忆、充当并发序点（Sequence Point） | **不执行具体耗时任务**（甚至不挂载 Bash 工具），仅负责对话与派发 | 轻量低延迟模型 |
| **Worker（隔离）** | 针对单个任务独立执行，挂载完整工具链 | 不直接向用户发送消息，统一向 Router 汇报结果；平级 Worker 之间不直接通信 | 高能力推理模型 |

- **请求批处理（Batching）**：当上一轮推理期间有多条新事件到达时，Router 在下一轮将积压事件合并注入。由于大模型 Prefill 阶段具备良好的并行计算特性，单次请求耗时随 Batch 增大的涨幅远低于线性增长，从而摊薄了单条事件的平均决策耗时。
- **扩展分片**：当团队规模继续扩大时，Router 可进一步做水平分片（Sharding），但会牺牲一部分跨分片的记忆连续性。

## 3. 事件驱动机制

系统的输入源从单一的人工提示词扩展为环境中的半结构化事件（Trigger），包括群聊消息、邮件、日程提醒、代码评审意见与 CI 构建结果。

### 3.1 两级事件过滤（Fast / Slow Path）

真实环境中的事件流具有"高噪声、低触发率"的特征，无法对每条事件都调用大模型判断：

- **程序过滤层（Fast Path）**：基于事件来源、群组范围、发送者白名单等确定性规则直接准入或丢弃。
- **语义过滤层（Slow Path）**：对通过初筛的候选事件，由模型根据自然语言策略判断是否需要发起动作。

### 3.2 Thread 线索与订阅直通

**Thread**：同一 PR、同一 IM 话题或同一邮件往来下的连续事件流。

- **未订阅状态（Slow Path）**：新 Thread 的首个事件经由 Router 评估并创建对应的 Worker。
- **已订阅直通（Fast Path）**：Worker 创建并订阅该 Thread 后，后续同 Thread 事件由程序直接路由给该 Worker，**不再经过 Router 中转**；当事件超出当前任务范围时，Worker 可退订或将其交回 Router。
- **统一收口输出**：虽然输入事件可直通 Worker，但对外输出仍由 Worker 汇报给 Router，由 Router 统一向用户回复并更新全局记忆。

### 3.3 上下文缓存管理：Inline、Spill 与链式召回

将模型上下文窗口视为容量受限的缓存进行管理：

- **内联（Inline）**：近期高频使用的信息直接放入上下文窗口，减少工具调用往返。
- **外溢（Spill）**：超出长度预算或低频的内容保存在窗口外，仅在上下文中保留唯一 ID 与简短摘要，按需读取。
- **链式召回（Chain of Recall）**：每个 Trigger、Thread 与 Worker Session 均分配唯一 ID，注入上下文时附带相邻一跳对象的 ID，形成引用图；模型可按需逐跳展开关联上下文。

### 3.4 预执行（Speculative Execution）

在用户尚未明确下达指令但意图概率较高时，后台预先消耗少量算力准备草稿，若用户确认则立即交付，若无需使用则静默丢弃：

- 日常日程场景：收到会议邀约时，后台自动核对日程冲突、检索参会背景并备好回复草稿。
- 研发排查场景：群内有人反馈报错时，后台先静默尝试复现与定位，若成功定位出简单修复方案则直接提交供审阅。

## 4. 全双工交互与多信道输出

### 4.1 异步全双工 ReAct 循环

传统 ReAct 循环在执行耗时工具时会同步阻塞。全双工循环将耗时操作拆分为异步的 `start()` 与 `stop()`：调用 `start()` 后立即返回已启动状态，循环继续响应用户的新输入；后台命令执行完毕后，其输出作为一条新事件重新投递回会话。

### 4.2 按信道区分输出密度

| 输出信道 | 表达规范 |
|---|---|
| 即时通讯（IM） | 保持低打扰，仅在需要人工决策或最终验收时发送通知；回复简明直接（原文限定单次回复不超过 100 词） |
| GitHub PR / 邮件 / 文档 | 高密度结构化交付：完整包含问题背景、修改说明与测试验证结果 |

## 5. 计算、状态与执行环境的解耦

1. **计算与状态分离**：Agent Loop 运行在无状态容器中，Session 状态持久化在外部数据库，进程重启或迁移不影响会话连续性。
2. **计算与执行环境分离**：考虑到用户的本地开发环境包含未提交代码、私有凭据、内网连接与专用硬件，无法整体搬上云端，因此在用户机器上仅部署**不保存会话状态的轻量执行守护进程**，负责接收命令并返回执行输出，支持个人电脑、内网主机与按需云算力统一接入（BYOM，Bring Your Own Machine）。

## 6. 外部看门狗（Watchdog）

在主系统之外独立运行一个定时触发的 Watchdog Session，构建外部控制回路（Control Loop）：

- 除检查进程存活外，重点**检查 Worker 是否取得实质进展、是否陷入无效重试循环或偏离任务目标**。
- 发现异常时主动介入修复，或允许维护者直接用自然语言向 Watchdog 询问故障原因、在线调整触发规则。

## 7. 原文合成负载实验数据

| 测试指标 | 实验结果 |
|---|---|
| 测试负载 | 模拟群聊 + GitHub CI 事件流，单轮约 300 条消息（含约 20 个真实工作请求），重复测试 5 轮 |
| Super-agent 双层架构 | 端到端完成时间 p50 **12.4 min** / p95 **15.7 min** |
| 单 Session + Subagent（中性提示词） | 5 轮测试中 **0 次**主动委派子代理，全部在主会话串行执行并被新消息频繁打断，p95 **29.5 min** |
| 单 Session（强制提示优先委派） | 5 轮中 4 轮委派，第 5 轮因模型自行判断"任务很小"而留在主会话执行，产生长尾延迟 |
| 关闭 Thread 直通的影响 | 完成时间基本不变，但 Router 决策次数增加 **30%**，缓存读取 Token 从 23.23M 增至 31.77M（**+37%**） |
| Router 批处理分摊效果 | 事件到达速率从 1 条/分升至 40 条/分时，平均 Batch 从 1.0 升至 2.8，单次请求耗时从 2.5s 增至 3.9s，折合单条决策耗时从 **6.4s 降至 1.6s** |

实验表明：仅靠提示词让单 Session 模型自行决定"是否委派子代理"并不稳定，必须在架构层强制隔离 Router 与 Worker 的职责。

## 8. 尚未解决的开放问题

1. **长程记忆与水平扩展**：跨数月周期的长期记忆压缩与检索机制，以及大规模场景下 Router 的分片边界。
2. **超越聊天窗口的交互形态**：在领域专用界面中实时协同、中途人工接管与任务调整的交互设计。
3. **跨实例协同（A2A）**：个人 Agent 实例与团队共享实例之间的通信协议与权限边界。
4. **安全与凭据保护**：事件驱动扩大了外部提示词注入的攻击面；同时，**一旦明文凭据进入模型上下文，就可能在正常对话或工具调用中意外泄露**，因此必须从机制上保证模型在使用凭据时不直接读取凭据明文。

## 9. 本系统对参考架构的取舍与改造

结合本仓库"单人使用、功能优先、优先复用开源组件"的定位（见 [设计原则](principles.md)），对上述机制的具体取舍如下：

| 参考架构机制 | 本系统对应设计 | 取舍说明 |
|---|---|---|
| Router / Worker 双层职责分离 | 工作站上的 DS-Bot 入口 + 工作站上的 Orca Worker（见 [系统拓扑](system-topology.md)） | **部分采纳**：入口与 Worker 分层，但两者同机部署；云端只做消息搬运 |
| Trigger 两级过滤 | 机器事件直接查 TOML 规则表；自然语言输入走受限意图分类 `decide()`（见 [架构总览 §2](architecture.md#2-意图分类与结构化路由)） | **改造采纳**：将开放式语义判断收敛为针对能力目录的 `kind` 分类 |
| Thread 线索关联 | 复用 Taskwarrior 的 `thread` 字段串联同一主题的子任务 | **简化采纳**：同 `thread` 内串行，不引入多对多订阅总线 |
| Inline / Spill 与链式召回 | 任务说明仅传递文件路径与一句话摘要；历史上下文通过 `kn recall` 按需检索 | **采纳** |
| 预执行（Speculative Execution） | 映射为任务库中带 24h TTL 的 `spec`（草稿）状态（见 [事件运行时与派发器 §2](event-runtime.md#2-状态机)） | **按需采用**：仅在邮件行程提取、会议准备等场景生成待确认草稿 |
| 异步全双工执行 | `evd` 投递 Orca Run 后立即返回，Worker 完成后异步调用 `ev done` 回写 | **采纳** |
| 多信道差异化输出 | IM 推送一句话摘要与三按钮卡片；代码与分析报告通过 Git PR 与 Markdown 交付 | **采纳** |
| 存算与执行环境分离 | **反向部署**：任务库、Orca 循环与本地文件全部留在工作站，云端仅保留等待队列（[ADR 0003](adr/0003-loop-local-entry-remote.md)、[ADR 0007](adr/0007-deferred-resident-node.md)） | **变体**：单用户本地自托管，避免跨机挂载本地文件与 GPU |
| 外部 Watchdog | 采用任务计划程序运行无状态巡检脚本（`ev-watchdog` 与 `hc check`），不维护常驻 Watchdog Agent 会话 | **简化采纳**：省去常驻会话的 Token 消耗 |
| 多实例分片与 A2A | 不引入 | 单人单实例无需分片 |
| 凭据隔离 | 凭据保存在 Windows 凭据管理器 / DPAPI 与各工具原生配置中，Agent 仅调用封装好的 CLI（如 `biliup`、`xxt`、`gh`） | **采纳** |

与面向研发团队的 Super-agent 原型相比，本系统额外引入了 **Taskwarrior 任务库**作为跨领域（涵盖日常事务、智能家居、内容创作与软件开发）的统一状态源。
