# 架构总览：基于事件的个人运行制度

本仓不是工具笔记的合集，而是一套个人运行制度的设计文档：定义**事件从哪来、谁来判定、谁去处置、如何落定、怎样反哺规则**。AI 协作、问题处理、日常生活不是三件事，是同一套机制的三个面：

- **AI 协作**：事件 → 简报 → 派 agent → 落定 → 记录。
- **问题处理**：事件 → 判定是否要人 → 升级或自办 → 留回退路径。
- **日常生活**：传感器、课表、平台通知、系统状态是事件源；墨水屏与主控台是呈现面。

现有的"入口 / 编排 / 执行"三层回答的是**谁来做**；本文补的是**什么触发做、做没做成、怎么不再犯**。两者不是替代关系——三层是事件模型里"处置"环节的一种实现。

状态：设计中（骨架定稿，P0 未实现） · 决策日期 2026-10-31 · 修订 2026-10-31（对齐 [Super-agent 架构参考](super-agent-architecture.md)）

骨架不是原创。它与 DeepSeek 产品部《Super-agent 设计探索》共享同一个判断：**单任务的上限是模型能力，多任务的上限是人的注意力**。因此凡是要绕开人的注意力瓶颈的地方——路由、订阅、投机、召回、自愈——两边的结构会自然收敛。差异在适用面：那篇文章面向团队研发协作，本文面向一个人的全部生活，所以多了"账"，也对模型能自动改什么更保守（见 §7.1、§11）。

## 0. 定位

三个具体的失效模式是这套制度的出发点：

1. **发生过但没人记得**。通知、提醒、异常只在当下被看见，事后无从追溯——没有账。
2. **有账但不闭环**。任务派出去，卡在中途，以"应该好了吧"收场——没有落定判据。
3. **闭环但不长进**。同样的故障第三次发生，规则没变——没有反哺。

上面三条其实是同一件事的三个阶段，而它们共同的根源是：**限制不在模型，在人的注意力**。人能同时跟进的活跃线索有限，所以系统必须自己记住发生了什么、自己盯到落定、自己把教训变回规则。

所以最小单位不是任务，而是**事件**。任务是一次处置，会话是一次交互，只有事件是"世界确实发生了某事"这个不可变事实。以任务为单位的系统有个结构性缺陷：任务的起点通常是人的一句话，凡是**不是人说出来的**事（磁盘满了、传感器触发、平台来消息、时间到了）都没有归属。以事件为单位，人只是事件源之一。

## 1. 五条不变量

制度的价值在于这些不许被打破的约束，而不是流程图画得多细。任何实现都必须满足：

| # | 不变量 | 违反的表现 |
|---|---|---|
| 1 | **先入账，再处置** | 处理到一半崩溃，事件消失 |
| 2 | **账只有一份，派生视图只读** | 各处缓存状态，互相对不上 |
| 3 | **判定确定性，模型只建议** | 同一个事件两次判定结果不同，事后无法审计 |
| 4 | **处置必须落定，不留悬挂状态** | 事件永远停在 `handling`，"应该好了"成为终态 |
| 5 | **规则改动由人确认，回退即停服务** | 系统自己改规则，出错后找不到原因 |

第 3 条是本文最容易被违反、也最不该让步的一条。见 §7.1。

**不变量只管结构，不管内容。** 第 4 条要求的是"每个事件最终必有终态"，而不是"终态必须附上能证明它对的材料"——后者是执行层的判断题，见 §8 开头。

## 2. 词汇（严格定义）

这些词在本仓所有文档里只有一种含义：

| 词 | 定义 | 不是 |
|---|---|---|
| 事件 | 不可变事实：某时某源发生了某事 | 不是消息，不是需求，不是愿望 |
| 账 | 事件的唯一持久化位置 | 原始事实不复制到各域；派生视图可缓存，不可写回 |
| 判定 | 事件 → 处置动作的映射 | 不是"让模型看看该干嘛" |
| 处置 | 执行判定结果 | 不是会话 |
| 落定 | 事件进入终态并留下一句结论 | 不是"应该好了"；也不要求能证明结论对 |
| 任务 | 一次需要多步执行的处置，落在 Orca | 任务不是事件 |
| 会话 | 人与 agent 的一段对话 | 会话不产生账，除非显式提事件 |
| 记录 | 落定后写下的复盘 | 与账分离，用于反哺 |
| 触发器（Trigger） | 环境产生、驱动系统行动的事件 | 不是提示词；本仓事件与之外延相同，但入账与判定严格分离 |
| Thread | 同一对象下的连续事件流：一个 PR、一个 IM 话题、一封邮件串 | 不是会话 |
| 订阅 | 处置方对某 Thread 的持续关注，命中即直通 | 不改变记账与落定 |
| 投机（spec） | 结果未定先做、有价值才交付的处置 | 不得写外部系统 |
| 回执 | 落定时留下的引用（提交、命令、路径、消息 id） | 不是门禁；可以为空 |

边界：**账只记事实，不记愿望**。用户说"我想做个视频"是愿望——可以是 `person.intent` 事件，也可以直接进任务；磁盘到 91% 是事实。混在一起，账就退化成待办列表，而待办列表不需要架构设计。

## 3. 主干

```
源 ──► 预过滤 ──► 入账 ──► 判定 ──► 处置 ──► 落定 ──► 反哺
      │  (确定性)  │        │        │        │
   白名单丢弃  幂等去重  规则表   规则/agent  回执
              边沿化   未匹配队列  /人       +deadline
                 ▲        │        │
        语义候选 ┘        └────────┴──► deferred ──► 到点召回 ──► 处置
                                                    └──► escalated ──► 人

已订阅 Thread 的后续事件:入账 ──► 直通处置(跳过判定)
```

每个箭头都有明确的所有者：

| 段 | 所有者 | 失败时的表现 |
|---|---|---|
| 入账 | `eventd`（常驻） | 源侧 spool 兜底，重启重扫 |
| 过滤 | 源侧白名单 + 语义层候选 | 噪音不进账；候选可被拒并留痕 |
| 判定 | 规则表（`policy/rules/*.toml`） | 未匹配进队列，不静默丢 |
| 处置 | 规则脚本 / Orca worker / 人 | timeout 转 deferred，不悬挂 |
| 落定 | 处置方写回 | 有终态即可；回执为空不阻塞 |
| 反哺 | 周报脚本 + 人 | 只产出候选，不自动改规则 |

## 4. 事件信封

入账的每条事件是一个固定结构的信封。payload 本身不内联进账，只存指针——账要小，查询才快。

| 字段 | 含义 | 约束 |
|---|---|---|
| `id` | 主键 | UUIDv7，按时间有序，便于分页与归档 |
| `ts` | 事件发生时间（源侧时钟） | 不可信时只作参考，判定用 `ingest_ts` |
| `ingest_ts` | 入账时间 | 由 `eventd` 写入，唯一权威时间 |
| `source` | 来源标识 | `home/<room>`、`system`、`im`、`agent`、`person`、`sched`、`platform/<名>` |
| `kind` | 事件类型 | `<域>.<对象>.<动作>`，如 `home.bedroom.motion` |
| `subject` | 受影响对象 | 设备 id / 仓库 / 任务 id / 人 |
| `severity` | `info` `notice` `action` `critical` | 决定通知通道与计龄规则 |
| `domain` | 归属域 | 工作 / 生活 / 设备 / 学习 |
| `payload_ref` | 原始 payload 文件路径 | 大对象一律外置 |
| `payload_hash` | payload 内容摘要 | 参与幂等键 |
| `dedupe_key` | 幂等键 | 源侧优先提供，缺省 `hash(source,kind,subject,payload_hash)` |
| `bucket` | 去重时间桶 | 同桶内同键视为同一事件，桶长由规则给 |
| `edge` | `rising` `falling` `sample` | 电平量必须边沿化后才入判定 |
| `corr_id` | 关联 id | 串联同一事务的多个事件 |
| `state` | 生命周期状态 | 见 §10 |
| `deadline` | 处置截止 | 逾期才升级，不是提醒 |
| `rule_id` | 命中规则 | 未匹配为空 |
| `task_ref` | 派发后的 Run/Dispatch | 账不复制任务状态，只存指针 |
| `thread_id` | 所属事件流 | 同一 PR / IM 话题 / 邮件串；无则空 |
| `subscriber` | 已订阅的处置方 | 非空时同 Thread 后续事件直通，不经判定（§6.8） |
| `spec` | 是否投机产出 | `true` 时必须带 `confirm_policy`（§8.3） |
| `parent_id` | 引用图上一跳 | 链式召回用；与 `corr_id` 区分：前者是检索链，后者是因果链 |

**存储**：统一数据根 `$AGENT_DATA`（拟定 `/data/Agent`，当前 `/data` 为空，以装机后的原生路径为准）。

- 账本：`$AGENT_DATA/events/ledger.db`（SQLite，WAL，单写者，无服务端）。
- payload:`$AGENT_DATA/events/payload/<yyyy-mm>/<id>.json`：保留 90 天（可配）。
- `sample` 类低频采样事件单独表，不进判定表、不与事实混排。
- 账本按月 compaction 到 `archive/<yyyy-mm>.jsonl.zst`，账本行永久保留（行本身很小）。
- 账与规则都不放在家目录下的散路径：`$AGENT_DATA` 独立于桌面环境，重装系统时只备份这一个目录即可恢复制度记忆。

选 SQLite 而不是消息队列或数据库服务：单机、单用户、要能 `sqlite3` 直接查、要能在宕机后直接读。**MQTT 只是设备面的传输层，不是账**——HA / Zigbee2MQTT / ESPHome 已经说 MQTT，不另造总线。

## 5. 分类学

六个正交维度。来源与领域由源给（信任由来源派生）；紧迫度、时效、可逆性、需要人由判定决定（源侧已知的紧迫度可预填）：

| 维度 | 取值 | 用途 |
|---|---|---|
| 来源 | device / system / person / agent / platform / schedule | 决定采集方式与配额 |
| 信任 | `trusted` / `untrusted`（由来源派生） | 派发前查一次：能否不经人确认自动执行；规则只能下调（[事件规格 §3](event-spec.md)） |
| 紧迫度 | `immediate` / `timed` / `digest` / `silent` | 决定递送方式与何时打扰 |
| 时效 | `now`（<1min） / `today` / `week` / `none` | 决定通知通道 |
| 可逆性 | `read` / `revertible` / `irreversible` | **决定是否需要人确认** |
| 需要人 | `auto` / `notify` / `confirm` | 与可逆性联合判定 |
| 领域 | 工作 / 生活 / 设备 / 学习 | 决定规则包与记录去向 |

可逆性是唯一带硬规则的维度，直接继承现有自动化边界：

- `read`：自动执行，事后记账。
- `revertible`：notify 后执行，必须附回退路径（停服务、快照、代际、撤销命令）。
- `irreversible`：必须人确认，无论规则怎么写；发布、推送、删除、转账、发消息都在此列。

## 6. 入账

### 6.1 传输面

| 面 | 适用 | 落地 |
|---|---|---|
| MQTT 桥 | HA / Zigbee2MQTT / ESPHome / BLE 网关 | `eventd` 订阅白名单 topic，转事件 |
| HTTP `POST /e` | 手机、其他机器 | 只绑 tailnet + 本机，带 token，不暴露公网 |
| spool 目录 | 只能用文件的源（cron、xxt、git hook） | `spool/inbox/*.json`，原子 rename 落地，`eventd` 消费 |
| unix socket | 本机 CLI | `$XDG_RUNTIME_DIR/event.sock` |
| 手工 | 人 | `ev add`，P0 阶段唯一入口 |

**先落盘再 ack**：任何入口都是"写进 spool 或事务提交后才回 200"。源侧失败必须重试，不允许"发了但没进去"。

### 6.2 电平转边沿

传感器与系统状态给的是**电平**（温度 26.3、磁盘 91%、在线），不是事件。全量入账会淹掉判定，所以：

- 只有**跨过规则声明的阈值 + 超过 hysteresis** 才生成判定事件。
- 未跨阈值的数据降级为 `sample`，按 1–5 分钟采样进采样表，用于看趋势，不参与判定。
- 每个阈值规则带 `cooldown`（默认 6h），避免在边界上反复触发。

这条决定了系统是"事件驱动"还是"日志驱动"。默认**不生成事件**。

### 6.3 源的沉默

事件系统只能对收到的事件反应，对"该来没来"没有反应——断网、账号失效、传感器没电，表现完全一样：安静。

所以每个源必须声明 `max_silence`，由外部检查点核对最后入账时间；超时产出 `system.source.silent`。这是事件模型唯一的盲区补丁，缺了它，"一切正常"和"全都断了"在账里无法区分。

### 6.4 去重与配额

- 去重：`dedupe_key + bucket` 唯一约束。源侧能提供幂等键的必须提供（如平台消息 id）；不能的用内容摘要加时间桶。
- 配额：**记账不设配额，通知设配额**。事实不许丢，但人可以被保护——通知侧按源令牌桶限流（默认 60 条/分，突发 20），超限合并为一条 `system.quota_exceeded` 事件并计数。

### 6.5 时钟

源侧时钟不可信（手机、嵌入式设备漂移，时区错配）。`ingest_ts` 是判定与计龄的唯一依据；`ts` 只用于展示和源侧排序。跨时区设备一律带偏移量上报，由 `eventd` 归一化。

### 6.6 源侧预过滤

入库之前，适配器按**确定性条件**丢弃：来源、群组、用户白名单、机器人名单。判据是配置，不是模型。

- 被预过滤的消息**不是事件**：不入账、不可查。这是全系统唯一允许"从未存在"的路径，因此配置本身必须可审计——谁在忽略哪类消息，要能一条命令列出来。
- 与 §7 的 `drop` 规则区别：`drop` 是入账后由规则裁掉，留下"我决定不理它"的统计；预过滤是根本不看。前者可复盘，后者不可。
- 预过滤只允许丢弃**批量、可再生成**的噪音（群聊闲聊、CI 成功通知）。任何来源只要能携带"人对我说的话"，就必须入账，交给判定。

### 6.7 语义层候选

对**不确定要不要起事件**的源（群聊、邮件串、平台评论），允许模型在预过滤之后给出候选：

- 候选必须带来源 id、命中理由、建议 `severity`，由规则或人确认后才入账。
- 模型不能决定 `severity` 的最终值，不能决定处置，不能跳过入账。
- 被拒的候选也记一条（`system.suggestion_rejected`），防止模型反复建议同一件事。
- 语义层的价值是**扩展性**：新增一条判断策略只需改提示词；但它只做准入建议，不做路由——路由仍归 §7 的规则表。

### 6.8 Thread 与直通

同一 `thread_id` 的后续事件，若该 Thread 已有 `subscriber`，由 `eventd` 直接投给订阅方，**跳过判定**。

- 仍入账、仍计龄、仍有 deadline——直通只省判定，不省账。
- 订阅是多对多：一个处置方可订阅多个 Thread；一个 Thread 可被多个处置方订阅，交集处的事件会同时直通，让它们各自发现冲突。
- 退订与交回：处置方判断事件超出范围时退订，事件回到 `triaged` 重新判定。
- 代价必须承认：直通旁路了规则，所以 `irreversible` 事件**禁止**直通；并需要一条直通率/直通后误判的周检（§11）。

## 7. 判定

### 7.1 为什么不用模型

判定必须**确定性、可审计、零成本**。同一个事件今天和明天判定结果不同，这套制度就不可信；用模型做路由，出错时无法回答"为什么走了这条路"。所以：

- **判定 = 规则表匹配**，纯函数，无网络。
- 模型的四个合法位置：①处置内部（写简报、拆任务）；②未匹配事件的**候选规则建议**；③交互层对话；④源侧语义层的**准入候选**（§6.7，仍不等于判定）。
- 模型永远不能直接写账、不能改规则、不能决定 `irreversible` 动作。

### 7.2 规则表

位置：`$AGENT_DATA/policy/`（git 管理，独立私有仓）。每个域一个文件，`rules/<domain>.toml`。

```toml
[[rule]]
id = "disk-pressure"
match = { source = "system", kind = "system.disk.pressure" }
when  = { path = "/", threshold_pct = 90, hysteresis = 3, cooldown = "6h" }
action = "notify"
channel = ["digest"]              # 不进即时通道
handler = "human"
deadline = "24h"

[[rule]]
id = "class-upcoming"
match = { source = "sched", kind = "sched.class.upcoming" }
when  = { lead = "30min" }
action = "dispatch"
brief_template = "templates/class-prep.md"
handler = "agent"
confirm = false                   # 只读准备,不写外部系统

[[rule]]
id = "publish-needs-human"
match = { kind = "platform.*.publish_request" }
action = "confirm"
handler = "human"
escalate_to = "im"
```

**匹配顺序**：显式 `rule_id` > 具体度（`kind + source + subject` 全匹配） > 域默认 > 全局兜底。同级冲突在加载时直接拒绝启动（fail closed），不允许"后写的覆盖先写的"。

**未匹配队列**：任何没命中规则的事件必须以 `state=triaged, rule_id=NULL` 留下，进入每页可见的"未分类"。这是规则集的缺口清单，不是错误日志。**禁止静默丢弃**——唯一能丢弃的是显式 `drop` 规则，且必须写原因。

## 8. 处置

**执行层不做正确性校验。** 基座保证的是"每个处置都会落定、都有记录"，不是"落定的都对"。理由：

- 机器能查的只有形式（有没有回执、退出码是不是 0），形式对而结果错是常态。
- 一旦落定需要"证明"，执行者会生产能过关的材料，而不是正确的结果——门禁越严，造材料越熟练。
- 正确性只有人知道。"这个修复对不对"不在任何 schema 里。能自动化的是存在性与可追溯性。

所以处置只需交两样：**一句话结论**（`summary`）和**可选的引用**（`refs`：提交、命令、路径、消息 id）。引用为空也接受，只是三个月后回看价值低——这个代价由周报统计出来给人看，不由系统拦。

三类 handler，只有这三种：

| handler | 适用 | 契约 |
|---|---|---|
| `rule` | 确定性动作（采样、汇总、调 HA service） | 必须幂等；退出码即结果；带 timeout |
| `agent` | 需要多步/需要判断（写代码、整理文档、调研） | 走 Orca 派发，复用"下发即监督"：必须监控到 `worker_done` 或证实退出 |
| `human` | 不可逆动作、需要价值判断、超时升级 | 通知带动作（确认/延后/拒绝），回复即落定或转 deferred |

三条复用现有链路的约定，不另立：

- **简报是最小下发单元**（目标/上下文/验收），不是逐条指令。
- **落定才允许报**：超时与失联是检查点，不是终态。
- **落定后释放 worker**，并产出任务记录。

### 8.1 事件默认不派生事件

否则一个 handler 再发事件、又触发规则，轻则风暴，重则环路。规则：

- 只有规则里显式声明 `emit` 的 handler 才能产生后续事件；
- 同一 `corr_id` 链深度上限 3；
- 超限丢弃并记 `system.chain_aborted`，必须人看。

### 8.2 处置的超时

每个 `handling` 事件必须有 `timeout`（由规则给，缺省 2×deadline）。超时不是失败，是**转 deferred 并升级**：`handling → deferred`，写 `wake_at`，同时通知人。系统里没有"卡住不动"的状态。

### 8.3 投机执行

投机不是第四种 handler，而是 `agent` / `rule` 上的一个标志位（信封字段 `spec`），必须带 `confirm_policy`。适用于只读与草稿类：

| `confirm_policy` | 适用 | 行为 |
|---|---|---|
| `auto` | 只读结论（核对日程冲突、检索背景） | 值得就推送，不值就静默 |
| `human` | 草稿类（回复草稿、修复方案、报告） | 产出后等人过目再发出 |
| `silent` | 复现与预判（先试着复现问题） | 成功才出现，失败不留痕 |

铁律：投机**不得写外部系统**、不得触发 `irreversible` 动作。"注意力免费"不等于"副作用免费"——省人的时间是目的，制造无法回退的改动不是。

### 8.4 全双工

处置不阻塞新事件：`handling` 期间同一会话仍可接收新事件；耗时命令异步化，完成时作为**结果回执事件**入账（同一 `corr_id`，不算派生，见 §8.1）。

这条针对的是最典型的失效：一个长任务把整个入口堵住，人以为系统死了。没有全双工，§10 的 deadline 只会变成更多超时。

## 9. 呈现面

呈现面是账的**只读派生视图**，不产生第二事实源（沿用 system-topology 的既有约束）。

| 面 | 能力 | 内容 |
|---|---|---|
| DS-Bot Web / Desktop | 读写（经链路回写） | 全部事件、任务卡片、可 reply 给 worker |
| IM | 只读 + 动作按钮 | 即时类事件；富内容渲染成图 |
| 墨水屏 | **只读** | 每日两帧：今日待处置 top N、逾期、昨日落定数 |
| ThinkSmart View | 读 + ack/defer/confirm | 桌面随手处置，不能派发新任务 |

**渠道带宽决定输出形态**：

- IM：只发需要决策或验收的内容，单条不超过 100 字，不贴推理过程与工具日志。
- 异步渠道（PR 评论、邮件、文档）：写完整背景、改动说明与验证结果。
- 推理与工具调用留在执行侧，不进任何对人的信道——这是 §8.4 之外的另一半：不只是不阻塞，还要不喧哗。

**首屏契约**：任何呈现面打开的第一屏只回答一件事——**现在有哪几件不能不管的事**。按 `immediate` 紧迫度、逾期时长、`critical` 顺序排列，最多一屏；其余靠翻查，不挤进第一屏。这条是为了对抗"入口一打开就满屏卡片"的失败模式：卡片越多，人越不读。

墨水屏在这里第一次有了明确职责：**它不是显示模块，是账的日视图**。这也统一了 `render-pipeline` 与各 `eink-*` 文档的位置——它们都是呈现面的实现，不是独立产品线。

## 10. 生命周期与召回

| 状态 | 进入条件 | 出口 |
|---|---|---|
| `new` | 入账 | 判定后 → `triaged` / `dropped`（显式规则，记原因） |
| `triaged` | 命中规则，等待处置 | handler 接单 → `handling` |
| `handling` | 处置中 | 处置方声明完成 → `resolved`；条件未到 → `deferred`；超时/报升级 → `escalated` |
| `deferred` | 等时间窗或等外部条件 | 到 `wake_at` → `triaged`（标 `recall`） |
| `escalated` | 交给人 | 人接手 → `handling`；直接判定 → `resolved` |
| `resolved` | 有结论的终态（回执可选） | 终结 |
| `dropped` | 显式规则或人 | 终结，必须写原因 |
| `expired` | 事件自身的有效期已过且未处置 | 终结，保留在账里可查 |

**计龄与强制升级**：

- `action` / `critical` 未落定 24h：进每日摘要。
- 未落定 72h：强制 `escalated`，不再等规则。
- `deferred` 逾期：`escalated`，不再静默重排。**延后不是取消，延后必须有下一次时间**。
- **过期与超时不是一回事**：`system.disk.pressure` 只说明当时磁盘紧张，两周后磁盘已清空，事件仍未落定——它该以 `expired` 收尾，而不是一直挂在逾期列表里。所以事件需要可选的 `valid_until`：
  - `timed` 类事件必须有 `valid_until`，过期即 `expired`，并在摘要里单独一栏"已失效"，不计入逾期。
  - 过期不等于忽略：`expired` 与 `resolved` 在周报里分开统计（前者说明系统在追已经消失的问题）。

**摘要通道**：每日 07：00 与 21：00 两帧（可配），内容是"逾期 > 今日待办 > 昨日落定"，而不是全部事件——全部事件在 Web 里，不需要被推。

### 10.1 按需召回

账要小，信息要全。两者靠**引用图**调和：

- 每个事件只内联下一跳关联对象的 ID（`parent_id`）：当前消息 → Thread → 相关任务 → 该任务关联的另一事件流。
- 模型或人沿引用逐跳展开，每跳只取摘要；需要全文时才读 payload。
- 这是把"上下文窗口当缓存"的思路用在召回上：常用在窗口内，低频留指针。它的价值不在日常，而在三个月后问"那次门锁异常最后怎么处理的"。

### 10.2 进展与偏离

进程活着不等于任务在做。长 `handling` 事件需要检查两件事，而不只是存活：

- **有无实质进展**：连续 N 个检查点的产物不变（无新文件、无新提交、无新输出）。
- **方向是否偏离**：产出与简报里的验收条件不再对应。

任一命中即 `escalated` 并附检查点差异。没有这一条，`timeout` 只能等到超时才生效，而无效循环往往在超时前就已经烧掉了大量时间。**检查由外部定时器驱动，不由处置方自己上报**——自己报进展的系统在失控时仍然只报进展。

## 11. 反哺

周报脚本（`ev report --week`）产出 `weekly-YYYYWW.md`，存记录层。指标不求全，只求能驱动一次规则修改：

| 指标 | 计算 | 用途 |
|---|---|---|
| 未匹配率 | 未匹配 / 总数 | 补规则或改注入 |
| 误报率 | 人工标 `dropped_incorrect` / 触发数 | 收紧阈值或加 cooldown |
| 超时率 | （`deferred` + `escalated`） / `handling` | 改 deadline 或拆任务 |
| 重复率 | 去重命中 / 总数 | 改桶长或改边沿参数 |
| 落定时长 | `resolved.ts − ingest_ts` 中位数 | 体验是否达标 |
| 直通误判 | 直通后转 `escalated` / 直通总数 | 订阅范围是否过宽（§6.8） |
| 投机命中 | 被采用 / 总投机 | 是否在浪费后台算力（§8.3） |
| 预过滤错杀 | 人工举报 / 预过滤总数 | 白名单是否过严（§6.6） |

**规则修改必须由人确认**——这是不变量 5。周报只产出候选（如"某规则一周触发 40 次、误报 31 次，建议停用"），不自动合并。规则仓的每次改动即一条决策记录，commit message 写"为什么改"，本仓不重复维护 ADR。

## 12. 域的挂载规则

一个域要满足八项才算域，否则它只是个脚本：

1. 事件类型命名空间（`<域>.<对象>.<动作>`）
2. 源与采集方式（MQTT / HTTP / spool / 手工）
3. 规则包（`rules/<域>.toml`）
4. 处置器（rule / agent / human 分别是什么）
5. 呈现面（可选）
6. 留痕去向（记录层哪个文件或目录）
7. 失败与回退（停用哪一段、数据是否保留）
8. 信任边界（哪些源不可信、正文如何当数据、执行方拿到什么权限，见 §12.3）

### 12.1 手机 agent（未来）

- **源**：`phone.notification`、`phone.location`、`phone.battery`、`phone.calendar`。
- **处置**：`phone.act`（如到家开灯、离校静音）。
- **硬约束**：账仍在工作站，手机只是源 + 执行端。手机不持有账——离线频率高、后台会被杀、凭证面大，让它记账等于制造第二事实源。
- 手机离线期间的事件由源侧本地排队，联网后按 `dedupe_key` 补投；`ingest_ts` 取补投时间，`ts` 保留原始时间用于展示。

### 12.2 智能家居

- **HA 是 device plane 的编排者，不参与判定**。HA 事件经 MQTT 桥转为 `home.*` 事件，规则包 `rules/home.toml` 决定动作，写动作由 handler 调 HA service。
- **HA 内只保留安全兜底**（断网、断电恢复、本地按钮），其余自动化一律上移到规则包。两套逻辑并存时以规则包为准，HA 侧自动化清单必须可枚举，避免"不知道谁在开关灯"。
- 传感器高频、电平性质强，边沿化与 cooldown 在 home 域是硬要求，不是优化。

### 12.3 信任：一道闸门

事件驱动把攻击面从"人说的话"扩大到"环境里的任何东西"。应对只有一条：**外部内容不能直接触发对世界的写操作**。派发前查一次 `trust`，不满足就转人；这个检查只有一处，不散落到各 handler、不按动作类别再分几级、不做运行时重校验（[事件规格 §3](event-spec.md)）。

配套的三条约束，都是"避免制造新泄露面"，不是"检查执行者"：

- **事件正文是数据，不是指令**。正文里的"请帮我做……"不改变任何规则；要改动就走规则与确认。
- **凭据不进事件**。payload 里不允许出现 token、密码、cookie。
- **执行方按最小权限运行**。worker 只拿到简报与所需路径。

单用户不等于低风险：账里有课表、位置、家庭状态。出网只走摘要，原文不出工作站。

## 14. 失败模式与对策

| 失效 | 后果 | 对策 |
|---|---|---|
| 事件丢失 | 该做的事没人做 | 先落盘再 ack；spool 重扫；源侧重试 |
| 重复处理 | 重复下单 / 重复通知 | `dedupe_key` + 幂等 handler + idempotency token |
| 处置卡死 | 事件悬挂 | 每 handler 有 timeout；超时转 deferred 并升级 |
| 告警疲劳 | 人开始全部忽略 | 通知配额 + 同类合并 + 分级通道 + 夜间静默（安全类除外） |
| 规则腐化 | 误报或漏报 | 误报率/未匹配率周报，规则需复审 |
| 事件风暴 | 系统互相触发 | 默认不派生事件；`emit` 需显式；`corr_id` 深度上限 |
| 账本膨胀 | 查询变慢 | payload 90 天、采样表独立、按月 compaction |
| 隐私外泄 | 原始数据出本机 | payload 本地；出网只走摘要；简报模板不带原文 |
| 单点失效 | `eventd` 挂全停 | 源侧 spool 兜底；呈现面只读不阻塞；账可直接 `sqlite3` 读 |
| 跨设备时钟错 | 计龄与排序错乱 | `ingest_ts` 唯一权威；`ts` 只作展示 |
| 预过滤错杀 | 该看的事从未存在 | 白名单可审计；`预过滤错杀`周报；重要来源一律入账 |
| 直通旁路判定 | 不可逆动作绕过确认 | `irreversible` 禁止直通；直通后 `escalated` 计入周检 |
| 投机副作用 | 后台改动无法回退 | 投机只做只读与草稿；写操作必须过规则与确认 |
| 无效循环 | 烧时间无产出 | 外部定时器查进展与偏离（§10.2），不靠自报 |
| 提示词注入 | 事件正文被当指令 | 正文只当数据；凭据不入 payload；执行方最小权限 |
| 源静默 | 断网/断电表现为"一切正常" | 每源 `max_silence` + `system.source.silent`（§6.3） |
| 账变垃圾场 | 过期未处理的事堆积，人不再相信账 | `valid_until` + `expired`，与逾期分栏统计（§10） |
## 15. 阶段

每阶段可独立停用；回退就是停服务，账不动，不迁移数据。

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0** 手工账 | `ev add/list/close` CLI + SQLite + 每日 digest 文本；不接任何自动源 | 连续一周，"事后才想起的事"都能在账里查到 |
| **P1** 常驻入账 | `eventd` + spool + socket；接两个真实源（学习通通知、系统状态巡检）；判定用手写规则 | 三个源的事件都走同一信封；未匹配队列有人看 |
| **P2** 派发闭环 | `agent` handler 走 Orca；`worker_done` 自动落定；超时转 deferred | 派发任务的落定率与超时率可统计 |
| **P3** 设备面 | MQTT 桥接 `home` 域；墨水屏日卡；ThinkSmart ack | 断网时本地兜底仍工作，恢复后账无缺口 |
| **P4** 反哺 | 周报脚本 + 规则候选，人工确认后合并 | 规则变更连续四周有据可查 |

P0 是唯一必须现在做的：它验证"事件模型对我自己是否成立"。如果一周后手工记账都嫌烦，说明问题不在工具，在制度粒度——那时应当缩小到两三类事件，而不是直接上常驻服务。

## 16. 未决项

1. **采样强度**：传感器 `sample` 流的采样率与保留期需实测，90 天可能过长。
2. **规则表达力**：TOML 谓词够不够；若需要脚本规则，得先有沙箱与只读约束。
3. **一事件多任务**：同一事件派多个 worker 时 `corr_id` 如何组织，尚未定。
4. **简报脱敏**：靠规则白名单，还是加一层自动脱敏，取决于实际出网内容。
5. **离线记账**：手机是否允许离线记账再补投，影响账的唯一性——倾向不允许。
6. **订阅的生命周期**：Thread 何时过期、退订后历史是否保留，尚无规则；参考文章也把 Worker 间协作列为开放问题。
7. **投机预算**：后台算力的上限（同时几个 spec、单次最长多久）未定；不设上限就与"省注意力"的目标背道而驰。
