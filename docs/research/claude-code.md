## 1 定位与体感

Claude Code 的形态是「**一个模型 + 一套规则 + 一堆生命周期钩子**」，而 2.1.318 这一版的重心明显从"编码助手"移到了"**可编排的 agent 运行时**"——证据是 `sdk-tools.d.ts` 里新出现的工具族（§3.3）：

- 编排：`Workflow`（脚本化 fan-out，带 resume 缓存）、`Agent`（子代理，后台默认）
- 调度：`CronCreate/CronDelete/CronList`、`ScheduleWakeup`、`Monitor`、`RemoteTrigger`
- 任务板：`TaskCreate/TaskGet/TaskUpdate/TaskList`（**带 blocks/blockedBy/owner 的依赖图**）
- 产物：`Artifact`（publish/list/read/watch/upload_asset/pin）
- 自我改进：`ProposeSkills`（提议新 SKILL.md）、`ProposeGoal`（提议完成条件）
- 隔离：`EnterWorktree/ExitWorktree`

体感上它把「人机闸门」做到了极致：33 个 hook 点、六档权限、三层规则、`PermissionRequest` 可代答、`updatedInput` 可改参、`updatedToolOutput` 可改结果。**但它的"真相"不在文件里**——`sessions.md` 明说 transcript 的 "entry format is internal to Claude Code and changes between versions, so scripts that parse these files directly can break on any release"【文档】。这跟 Codex 把 `exec_events.rs` 当对外契约正好相反。

对我们的直接含义：**Claude Code 的扩展面是"事件"，Codex 的扩展面是"协议"**。我们要抄 Claude 的**闸门语义**，抄 Codex 的**协议稳定性**，两者不要混。

## 2 架构

### 2.1 形态

```
npm 包（29KB） ──postinstall──► 平台原生二进制（win32-x64 解包 342MB）
                                      │
        ┌─────────────────────────────┼──────────────────────────────┐
        │                             │                              │
   CLI TUI（交互）            claude -p（非交互）              Agent SDK / IDE / Desktop
        │                             │                              │
        └──────────── 同一套 hooks + permissions + sessions ─────────┘
                                      │
                    ~/.claude/  （settings.json / CLAUDE.md / agents/ / skills/ / projects/…）
```

【文档】hooks.md 开篇明说 hooks 在"terminal sessions, IDE extensions, Desktop app, cloud sessions"里**是同一套事件**——这对我们是重要参照：**闸门不该按前端分裂**。

### 2.2 配置分层（settings 五源）

【文档】permissions.md「Hook locations」表 + 「Settings precedence」：

| 层 | 位置 | 可否被下层覆盖 |
|---|---|---|
| managed policy | 平台路径 / `managed-settings.json` | 最高，`allowManagedPermissionRulesOnly`/`allowManagedHooksOnly` 可关死下层 |
| user | `~/.claude/settings.json` | 可 |
| project | `.claude/settings.json` | 可 |
| local | `.claude/settings.local.json`（gitignore） | 可（但被 git 跟踪时按仓库内容对待，需 workspace trust） |
| CLI | `--settings`、`--allowedTools` 等 | 不可覆盖 managed 的 deny |

【文档】关键细节：**hook 条目是"合并"而非"替换"**——user/project/local 各自 append，managed 的不会被 `disableAllHooks` 从外部关掉（hooks.md "Hook entries merge across settings levels rather than replacing each other"）。

### 2.3 我们的映射

`aica-pi/policy.json`（v2 §2.6-30 设想）本质是 managed 层的一个极简版。v2 只设计了一个 `max_permission` 封顶键。**建议按 Claude 的三件事拆**：

1. `policy.json.permissions`：deny/ask/allow 三段（顺序固定 deny→ask→allow），比 `max_permission` 更能表达"这类永远拒、那类永远问"；
2. `policy.json.hooks_only`：只允许包内 hooks（对应 `allowManagedHooksOnly`），v2 §2.6-28 已想到；
3. `policy.json.disabled_hook_ids`：显式关掉某几个 hook 点（对应 `disableAllHooks` 的定向版）。

成本：一个 JSON schema + gate.ts 读一次。收益：以后加"团队策略"不用改代码。

## 3 核心机制

### 3.1 会话主循环、turn 边界与取消

**turn 边界**由 hook 的三档"节奏"定义（【文档】hooks.md "Hook lifecycle"）：

- **per session**：`SessionStart` / `SessionEnd`
- **per turn**：`UserPromptSubmit` → （agentic loop）→ `Stop` / `StopFailure`
- **per tool call**：`PreToolUse` / `PostToolUse`（`EndConversation` 例外，两者都跳过）

`UserPromptSubmit` 的一个重要语义【文档】：它 "Also fires on turns Claude Code starts on its own" ——**自启动的 turn 与用户 turn 走同一个入口**。这是让"定时任务/loop/唤醒"不产生第二套路径的关键。

**取消**没有独立事件，靠三处表达：

1. `Stop` hook 的 `decision:"block"` 可以**阻止停下**（"Prevents Claude from stopping, continues the conversation"）；
2. `StopFailure` 按错误类型分类（matcher 值 `rate_limit/overloaded/authentication_failed/max_output_tokens/…`）；
3. `--max-turns` / `--max-budget-usd` 这类 run 级限制【日志】sessions.md 提到它们会阻止 `--resume` 直接 attach 运行中的 background session。

**我们怎么改**（G4/S3）：v2 的 abort 只写 `failed("aborted by user")`。抄两条：

- **取消原因分类**进 `result.reason`：`user` / `timeout` / `budget` / `replaced`（对齐 Codex 的 `TurnAbortReason`，见 codex.md §3.1）；
- **`stop` 可被拦截**这一条反过来用：我们的 `node_settled` hook（S15）如果返回 `{"continue":false,"stopReason":"..."}`，应当能**阻止 result 落盘**（把节点留在 running 或改判 failed）。这给"验收不过关不许收工"提供了一个不需要改 worker 的位置。

### 3.2 上下文注入与压缩

#### 3.2.1 CLAUDE.md 的注入方式（这是最值得抄的一条机制）

【文档】memory.md 两处硬事实：

1. **投递形态**："CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself."
2. **拼接顺序**：从文件系统根到工作目录**全部拼接**（不覆盖），同级目录内 `CLAUDE.local.md` 追加在 `CLAUDE.md` 之后；子目录的 CLAUDE.md **不预载**，等 Claude 读/写/编辑该子目录下文件时才载入。

另有三个工程细节，全部可抄：

- `@path` import 最大深度 **4 跳**，代码块内的 `@` 不算；import **不减少** context 成本（被导入文件与导入者一起载入）；
- **块级 HTML 注释在注入前被剥掉**（`<!-- maintainer notes -->`），代码块内的保留——这是"给人看的注释不占 token"的现成做法；
- 单文件 > **4 MiB 直接整份跳过**；按需加载的文件（子目录 CLAUDE.md、path-scoped rules）另有字符上限：200K 上下文窗口下 **40,000 字符**。

#### 3.2.2 AGENTS.md 是"插件"，不是内建

【文档】memory.md：AGENTS.md 由内建插件 `cc-plugin-agents-md@builtin` 读取，`/config` 的 **Project instructions** 四值：`claude-md-or-agents-md`（默认）/`claude-md-and-agents-md`/`claude-md`/`managed-only`。默认含义：**有 CLAUDE.md 就只读 CLAUDE.md，没有才读 AGENTS.md**（v2.1.277+）。

对我们的直接含义：**不要为"读 AGENTS.md 还是 CLAUDE.md"改 daemon 代码**。我们已有 `aica-pi/prompts/worker.md`，把"项目指令文件发现顺序"做成一个可配置的 loader（`spec.instructions: "agents-md"|"claude-md"|"both"`），默认 `agents-md` 即可。

#### 3.2.3 压缩存活表（v2 完全没写，直接可用）

`/compact` 之后各类内容的处置【文档】context-window.md「What survives compaction」：

| 内容 | 压缩后 |
|---|---|
| system prompt / output style | 不在消息历史里，原样 |
| 项目根 CLAUDE.md + 无 paths 的 rules | **从盘重新注入** |
| auto memory | **从盘重新注入** |
| plan mode 写下的 plan | **从盘重新注入** |
| 带 `paths:` 的 rules | 等 Claude 读到匹配文件时重载 |
| 子目录 CLAUDE.md | 等读到该子目录文件时重载 |
| Claude 读/编辑过的文件 | **最多重读 5 个，按最近修改排序** |
| 已调用的 skill 正文 | 重新注入，每 skill ≤5,000 token、合计 ≤25,000 token，超了从最旧丢 |
| 早先 hooks 注入的 context | 被摘要掉 |

另【文档】同页：自 v2.1.198 起"摘要请求继承会话的 extended thinking 配置"。

**我们怎么改**（G2 投影 + G22/S12 经验注入）：这张表直接回答了 v2 的一个悬空问题——「经验注入放哪」。v2 §2.5-26 的判断是对的（"rules/经验注入放 userMessage 尾部（pi compaction 不动 user 消息）"），但更稳的做法是抄 Claude 的**"从盘重注入"**：

- `learned.md`、`worker.md`、`spec.goal/accept` 这三段**不放进 userMessage**，而是每次 spawn 时由 daemon 重新拼（我们现在就是这样，保持）；
- 关键是**压缩后要重拼一次**：pi compaction 之后当前进程的 prompt 不会变，但我们的 worker 是"多轮重拉"模型（v2 G5 定性为设计），下一次 spawn 天然重拼。所以**这一条我们已天然满足**，只需在 `events.jsonl` 的 `compaction` 事件里记 `tokens_before/after`，让 UI 能解释"为什么下一轮像换了个脑子"；
- 反过来要注意：**skill 正文有 25k token 合计上限**（Claude 的做法）。我们 S14 要挂 `--skill`，若将来挂多个，要预算化（≤3 个 / 合计 ≤25k 是合理起点）。

#### 3.3.2 规则语法与求值（`permissions.md`）

- 求值序 **deny → ask → allow**，**特异性不影响顺序**："A broad deny rule like `Bash(aws *)` blocks every matching call, including calls that also match a narrower allow rule like `Bash(aws s3 ls)`."
- **裸工具名 deny 会把工具从上下文里摘掉**（"removes the tool from Claude's context entirely"）；带作用域的 deny（`Bash(rm *)`）保留工具、只挡调用。→ 对我们的含义：**"禁用某工具"与"某工具某些参数禁"是两种实现**，前者应体现在 spawn 的 `--tools` 白名单里，后者在 gate。
- 参数匹配 `Tool(param:value)` **只对 deny/ask 有效**，且**不能匹配主内容字段**（Bash 的 `command`、Read/Edit/Write 的 `file_path`、WebFetch 的 `url`）——理由是"`Bash(command:rm *)` would be bypassable by a compound command"。→ 我们的 `spec.rules` 正则在 `JSON.stringify(args)` 上匹配，**天然会踩这个坑**（复合命令可绕过）。v2 §2.2-8 的 stream-rules-lite 要么明确只做"提示性守门"，要么先做命令拆分（见下条）。
- **复合命令拆分**：识别 `&& || ; | |& &` 与换行，**每个子命令都要通过才放行**；`npm test &&` 这种悬空被认为 unparseable，allow 规则不生效。
- **包装器剥离**（仅 allow 规则）：`timeout time nice nohup stdbuf command builtin`、zsh `noglob`、裸 `xargs`，以及"已知安全环境变量赋值"（`NODE_ENV=test npm test` 能匹配 `Bash(npm test *)`）；deny/ask 则能穿透**任意**前缀赋值（`FOO=bar rm -rf tmp/` 仍命中 `Bash(rm *)`）。
- **通配符语义**：`*` 可出现在任意位置；`Bash(ls *)` 匹配 `ls` 也匹配 `ls -la`，但不匹配 `lsof`（空格是规则的一部分）；`Bash(ls*)` 匹配 `lsof`；`:*` 后缀等价于尾部 `*`。

**我们怎么改**（G31 stream-rules-lite + G33）：v2 的 `spec.rules:[{pattern,message}]` 正则方案有三个可预见的洞，按 Claude 的做法补：

1. **拆分子命令再判**：`rules` 命中判定前，先按 `&& || ; |` 切分，任一段命中即 block。成本约 30 行（不追求完整 shell 解析，只做引号外的分隔符切分）；
2. **只把正则当"提示性守门"**：`{block:true, reason}` 对模型是提示，不是安全边界。真正的安全边界是 `fs_scope`/`deny_paths`/`--tools`（见 codex.md §3.3.1）；
3. **`deny` 与 `always_ask` 穿透前缀赋值**：`FOO=bar rm -rf` 必须命中。

#### 3.3.3 审批卡的四类决定动作（hooks.md 决策矩阵）

【文档】hooks.md 的 decision control 表把"能改什么"分得很细：

| 事件 | 能做什么 | 字段 |
|---|---|---|
| `PreToolUse` | 允许/拒绝/转人工/**改参**/注入上下文 | `permissionDecision: allow\|deny\|ask\|defer`、`permissionDecisionReason`、`updatedInput`、`additionalContext` |
| `PermissionRequest` | **代答**（allow/deny）+ 改参 | `decision.behavior`、`decision.updatedInput` |
| `PermissionDenied` | 告诉模型"可以重试" | `hookSpecificOutput.retry: true`（且"Claude Code ignores `retry` when the classifier produced no verdict"） |
| `PostToolUse` | **改结果** | `updatedToolOutput` |
| `MessageDisplay` | 只改**显示**，不改 transcript/模型所见 | `displayContent` |

另外**每个事件都可阻塞或不可阻塞**（hooks.md 的 exit-code-2 表，22 行）：`PreToolUse`/`UserPromptSubmit`/`Stop`/`SubagentStop`/`TeammateIdle`/`TaskCreated`/`TaskCompleted`/`ConfigChange`/`PostToolBatch`/`PreCompact`/`PreModelSwitch`/`Elicitation`/`ElicitationResult`/`WorktreeCreate`/`WorktreeRemove` 可阻塞；`PermissionRequest` **不可**（"Exit code 2 isn't honored for this event"）；`PostToolUse` 不可（工具已跑）。

**我们怎么改**（S4/S5 深化）：

1. **`defer` 值得抄**：`permissionDecision:"defer"` 是"这次不决定，交回正常流程"。我们的 gate.ts 有个真实场景：`gate-req.json` 写不出去时 v2 设计是 fail-closed block。改成 **defer** → 记 `approve_defer` 事件、不 block、让 worker 继续 → 由 S10 的节点行显示"审批通道不可用"。理由：block 会让 worker 误以为被拒而改道，丢了本来能做的事。
2. **`updatedInput` 值得抄一半**：我们的 gate 现在只能 allow/deny。加 `gate-ans.updated_args` 让审批人**改命令再放行**（如把 `rm -rf build` 改成 `rm -rf build/tmp`）。实现是一次 `JSON.parse` 覆盖，成本极低，收益是"拒绝"不再是唯一表达。
3. **`retry:true` 的语义**：worker 被 deny 后，我们的 gate 只回 `{block:true,reason}`。pi 的 `block` 已经等于"回给模型一句话"，所以 **block 就是 retry 许可**——但要在 reason 里显式写"你可以换个方式重试"，否则模型容易理解成"此路不通"。

#### 3.3.4 六档模式的真实差异（permission-modes.md）

| 档 | 不问了跑什么 | 我们是否要这一档 |
|---|---|---|
| `default`(Manual) | 只读 | ✅ 我们的 `supervised` |
| `acceptEdits` | 读 + 文件编辑 + 常见文件系统命令（`mkdir/touch/mv/cp`） | ✅ 我们的 `edits` |
| `plan` | 读 + （有 auto 时）分类器批准的只读命令 | ✅ 见 §3.4 |
| `auto` | 全跑，但 shell/网络动作前过分类器 | ⏸ R2（需 guardian，见 codex.md §3.3.4） |
| `dontAsk` | 只跑不需授权的 + allow 规则命中的，其余**拒** | ✅ 我们的 CI 档（**值得单独一档**，v2 三档里没有） |
| `bypassPermissions` | 全跑（含写 protected paths） | ✅ 我们的 `full` |

**v2 的三档（supervised/edits/full）漏了 `dontAsk` 这一档的价值**：它不是"更松"，而是**"无人值守时把'会问'降级为'拒'"**。我们的 daemon 在夜间跑长任务时正需要这个：与其让 worker 卡在 gate 上 5 分钟超时，不如立刻拒并让它记录"需要人处理"。建议 `spec.permission` 扩为四值：`supervised | edits | full | ci`（ci = 会问即拒 + 超时立刻 deny）。

#### 3.3.5 protected paths / critical paths（v2 只写了一半）

【文档】permission-modes.md 两张表：

- **protected paths**（写永不自动批，除 `bypassPermissions`）：`.git`、`.config/git`、`.vscode`、`.idea`、`.husky`、`.cargo`、`.devcontainer`、`.yarn`、`.mvn`、`.claude`（有例外：worktrees、plan 文件、scratch、memory 目录）；protected files 包括 `.gitconfig`、shell rc 全家、`.npmrc/.yarnrc/.pnp.*`、`.pre-commit-config.yaml`、`.mcp.json`、`.claude.json`、以及**通过 `--settings`/`--mcp-config`/`--agents` 传入的文件本身**。
- **critical paths**（`rm`/`rmdir` 的目标）：文件系统根、**根的直接子目录**、家目录（含 Windows 8.3 短名）、Windows 盘符根与其顶层目录、工作目录及其祖先；还有一堆"变量展开后可能变成根"的形态（`rm -rf "$DIR"/*`、`rm -rf "$(pwd)"`）。规则是 **"No allow rule or PreToolUse hook `allow` approves one"**——连 hook 都无权放行。

**我们怎么改**（G33 的具体化）：v2 的默认 `deny_paths` 是 `.env`、`*.pem`、`~/.ssh`——**太窄，且全是"读"敏感而不是"写"敏感**。按 Claude 的表改成两组：

```jsonc
// aica-pi/policy.json
{
  "protected_paths": [".git", ".claude", ".vscode", ".husky", ".cargo"],   // 写：任何档都问/拒
  "protected_files": [".gitconfig", ".npmrc", ".envrc", ".mcp.json"],
  "critical_paths": { "enable": true, "extra": ["<run_root>"] }           // rm/rmdir 目标命中即硬拒
}
```

`critical_paths` 值得单独实现：它是**唯一能挡 `rm -rf` 的本地机制**，而我们的 worker 有 `bash` 全权。实现是 gate.ts 里对 `bash` 的 args 做一次 `rm\s+-rf?\s+(...)` 提取 + 路径归一化比对，约 40 行。**这条比 S4 的整个审批门更值**，因为审批门可以被 `allow_session` 绕过，critical check 不会。

### 3.6 hooks 生命周期事件清单（33 个，【文档】hooks.md）

按节奏分组：

| 节奏 | 事件 |
|---|---|
| per session | `SessionStart`(matcher: startup/resume/clear/compact/fork)、`Setup`(init/maintenance)、`SessionEnd`(clear/resume/logout/prompt_input_exit/other) |
| per turn | `UserPromptSubmit`、`UserPromptExpansion`(matcher=命令名)、`Stop`、`StopFailure`(matcher=错误类型 12 值) |
| agentic loop（每次工具调用） | `PreToolUse`、`PermissionRequest`、`PermissionDenied`、`PostToolUse`、`PostToolUseFailure`、`PostToolBatch`、`SubagentStart`、`SubagentStop`、`TaskCreated`、`TaskCompleted`、`TeammateIdle` |
| 独立/异步 | `Notification`(matcher 11 种)、`MessageDisplay`、`InstructionsLoaded`、`ConfigChange`、`CwdChanged`、`DirectoryAdded`、`FileChanged`、`WorktreeCreate`、`WorktreeRemove` |
| 上下文/模型 | `PreCompact`、`PostCompact`、`PreModelSwitch`、`PostModelSwitch` |
| MCP | `Elicitation`、`ElicitationResult` |

配套机制（全部【文档】）：

- **matcher 语义**：只含字母/数字/`_`/`-`/空格/`,`/`|` → 精确匹配或 `|`/`,` 列表；含其它字符 → **JS 正则、非锚定**（"`Edit.*` matches both `Edit` and `NotebookEdit`"）。
- **`if` 字段**：用权限规则语法做二级筛选（避免无谓进程 spawn）。
- **并发**：事件内 hook 并行；**超过 12 个 prompt/agent 类 hook 时，12 个先跑**，其余等空位，超时从各自开始算。
- **超时**：600s（command/http/mcp_tool）、30s（prompt）、60s（agent）；`UserPromptSubmit`/`PreModelSwitch`/`PostModelSwitch` 降为 30s；`MessageDisplay` 10s；`SessionEnd` 共享 1.5s 预算（可被单个更长 timeout 抬到 60s）。
- **输出上限**：`additionalContext`/`systemMessage`/`initialUserMessage`/纯 stdout 各自 **10,000 字符**上限，超了写文件 + 前 2,000 字符预览（"This cap has no setting or environment variable to raise it."）。
- **`terminalSequence`**：hook 只允许发 OSC `0/1/2/9/99/777` 与 BEL（桌面通知、标题、进度），**不允许 CSI/OSC 52**——这解决了"hook 没有控制终端"的问题，且在我们的 WebView 壳里等价物是 `Notification` API。
- **`SessionStart` 的额外能力**：除 `additionalContext` 外还能给 `initialUserMessage`、`watchPaths`、`sessionTitle`、`reloadSkills`。
- **信任**：`allowManagedHooksOnly` 只放行 managed；`disableAllHooks` 在 managed 之外关不掉 managed hook。
- **resume 语义**：`SessionStart` 在 resume 时会带 `source:"resume"`（`--fork-session` 时 `"fork"`）**重新跑**；而中途事件注入的文本在 resume 时**被重放而不是重跑**（"replays the saved text rather than re-running the hook, so values like timestamps or commit SHAs become stale"）。

**我们怎么改**（G37/S15）：v2 的 4 个点（`node_start`/`pre_tool`/`node_settled`/`gate_raised`）站得住，补三条：

1. **hook 输出也设 10k 字符上限 + 文件溢出**。我们的 hook stdout 现在是裸 `JSON.parse`，一个 bug 的 hook 回 10MB 会把 daemon 拖死；
2. **`node_start` 的 `additionalContext` 要能改 `already_known`**（Claude 的 `SessionStart.additionalContext` 就是这个位置）——这比 v2 说的"可注入 already_known"更具体：它是**hook 返回值**，不是 spawn 参数；
3. **不要做 `SessionStart` 式的"resume 重跑"**：我们的节点重拉就是"新 turn"，没有 resume 概念，硬造会得到"hook 重跑改写了历史注入"的不一致。保持"每次 spawn 都跑 node_start"最简单且自洽。

#### 3.7.1 transcript

**我们怎么改**：这条是**反面教材 + 正面确认**。反面：我们的 `stdout.log` 就是"内部格式"，v2 S2 说要"按行 readline 转写"，那就必须在**转写器里做版本容忍**（未知事件类型 → `{kind:"unknown",raw}`，不抛错、不断流）。正面：`events.jsonl` 应当**显式声明契约**——在 `src/envelope.ts` 里写 `EVENT_VERSION = 1`，每条 event 带 `v:1`，UI 遇到 `v>1` 显示"需要升级 workbench"而不是崩。

#### 3.7.2 checkpoint / rewind（v2 未收录）

【文档】checkpointing.md：

- **每个 user prompt 一个 checkpoint**；每会话保留**最近 100 个**快照；与 session 一起 30 天清理。
- `/rewind`（或空输入时 `Esc Esc`）菜单六项：恢复代码+对话 / 只恢复对话 / 只恢复代码 / **从这里开始摘要** / **摘要到此为止** / 取消。
- "只恢复代码"两项**仅当该 checkpoint 记录了文件变更时出现**。
- 快照文件以"每个文件的第一份快照"作为 VS Code 会话 diff 的基线。

**我们怎么改**（G40）：这是**比 git hidden refs 便宜得多**的方案，而且和我们"节点目录即真相"完全同构：

- 节点内 `attempts/<n>/artifacts/` 每轮快照（只快照 worker 声明产出的路径，不是整个仓）；
- `/api/runs/<r>/node/<p>/rewind` → 把 `attempts/<n>/artifacts` 拷回工作区 + 把 `result.json` 归零重拉（session 用 fork 目录，见 codex.md §3.7.2）；
- "摘要到此为止"这一项直接对应我们把 `events.jsonl` 前 N 条压成一段 `spec.already_known`——**Claude 把"压缩"做成了可手选的区间**，这个交互比"自动压缩"可信得多。

### 3.8 UI / TUI、diff、等待态

- **状态栏**：`statusline.md` 里 status line 命令能拿到 `transcript_path`、context 用量、cost、git 状态（sessions.md §Access conversations from scripts 引用）。
- **diff 呈现**：VS Code 侧"inline diffs"，Desktop 侧"visual diff review"（llms.txt 各页摘要）；TUI 侧【日志】有 `/diff` 实时面板（whats-new 2026-w36 "watch Claude's edits in a live /diff panel"）。
- **等待态**：【日志】`spinnerVerbs` 可替换 spinner 词、`Compacting...` 是独立 spinner 文案（2.1.305 修 "spinner cutting off 'Compacting...'"）；`MessageDisplay` 允许 hook **只改显示不改 transcript**（§3.3.3）。
- **通知**：`Notification` hook + `terminalSequence`（OSC 9/777）→ 桌面通知；`PushNotification` 工具（`:3250-3256`，`message` <200 字符，`status:"proactive"`）是**模型主动推送**到手机。

**我们怎么改**（G17/S13 + UI）：

1. 状态栏的等价物是 `apiView.runHeader`：把 `Σtok / 上下文用量 / live worker 数 / 待答审批数` 四个数放一行，比现在的 `dur` 单值有用得多；
2. `MessageDisplay` 的"只改显示"隔离值得抄到 steps 渲染：**折叠/摘要显示不得改动 `events.jsonl` 原文**，否则 transcript tab 与 steps 会打架；
3. `PushNotification` 的 200 字符上限 + `proactive` 标记，是"模型主动找人"的最小契约。我们的 `ev_notify{text}` 应照抄这个上限（超了截断），并区分 `proactive`（模型主动）与 `blocked`（卡在审批）两种，通知文案不同。

## 4 UI 侧的三个具体结论

1. **审批卡 = 服务端给的选项菜单**（§3.3.3）：`opts[]` 由 gate.ts 生成，前端只渲染；永远追加一个自由输入框当"Other"。
2. **每步可见、每步可折叠，但折叠不改真相**（§3.8 第 2 点）：steps 是投影，transcript 是原文。
3. **等待态要有"多久没动静"**：Claude 的 spinner 文案（`Compacting...`）与 status line 的 context 用量，合起来就是"用户知道 agent 在干什么"。我们最少要有：当前工具名 + 已耗时 + 上下文用量。

## 6 不抄

| 不抄 | 原因 |
|---|---|
| 33 个 hook 事件全量 | 文件态 daemon 没有"模型请求前/显示时"这些点；4 个点覆盖 80% 价值 |
| `auto` mode 分类器（R1） | 需要第二模型在线评审，成本与误判都高；先落 `ci` 档与 guardian-lite（codex.md §3.3.4） |
| `bypassPermissions` 的"连 protected paths 也放行" | 我们的 shell 壳没有容器隔离，这个档给不了任何安全兜底；`full` 档也应保留 critical paths 检查 |
| transcript 格式 | 官方自己都说格式会变；我们只抄"路径按项目分目录 + 30 天保留"的形状 |
| `Artifact`（发布到 claude.ai） | 云侧能力，与"本机单人"定位冲突 |
| `EnterWorktree` 作为模型可调工具 | worktree 生命周期应由编排器管（我们的 G20），不该让 worker 自行切换 |
| 44 个工具全量照搬 | 真正要抄的是 **schema-as-source-of-truth + 每个字段带 doc 注释** 这个做法，不是工具清单 |
| `SessionStart` 在 resume 时重跑 hook | 我们无 resume 语义，硬造会不一致 |
