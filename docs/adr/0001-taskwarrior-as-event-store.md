# ADR 0001：使用 Taskwarrior 3 作为任务库，不自建事件存储

系统需要一个支持跨设备访问、历史回溯、延迟唤醒与周期调度的任务状态存储。候选方案包括自建 SQLite/PostgreSQL 事件表、Home Assistant Todo 组件与 Taskwarrior 3。

最终选用 **Taskwarrior 3**（底层存储为 `taskchampion.sqlite3`）。它原生提供了延迟唤醒（`wait`）、周期任务（`recur`）、自定义字段（UDA）、任务依赖（`depends`）、注解（Annotation）以及变更钩子（Hooks），直接覆盖了任务管理系统最核心的状态流转需求，省去了从头实现事件溯源（Event Sourcing）与定时唤醒逻辑的维护成本。

对应的工程折衷：Taskwarrior 本质上是命令行待办工具，不具备分布式事务日志，Hook 采用外部进程同步调用，且并发写入存在文件锁竞争。我们在架构上通过三项措施补齐：将九态状态机映射到原生的 `status + start + tags`、以 `thread` 字段作为串行并发边界、将复杂任务的中间执行过程交由 Orca 管理。

**记录原因**：后续维护时很容易产生"把待办工具替换为完整事件溯源数据库加消息队列"的冲动。本记录明确：在单用户规模下，引入重型存储与消息中间件只会增加运维负担；若未来出现瓶颈，应优先替换上层编排或外围接入组件，保持底层任务库精简。
