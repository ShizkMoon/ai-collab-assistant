# 路线图：P0 起步与判据

> 状态：设计中 · 上游：[架构总览 §15](architecture.md)、[事件规格 §8](event-spec.md)

本仓已有足够的设计，缺的是**一次能证伪的经验**。本文把 P0 写成一周内可执行、可判定成败的实验，并规定失败时怎么收缩。

## 0. 目的

不是验证工具，是验证**事件模型对我自己是否成立**。这个问题只能在用了一周之后回答，靠继续写文档回答不了。

三个子问题，按重要性排序：

1. 我会不会记？（不做任何自动化的情况下，能否坚持记下"事后才想起的事"）
2. 记下来有没有用？（一周后回看，账里有没有真能避免漏掉的东西）
3. 粒度对不对？（记的东西是太细、太粗，还是刚好）

第 3 个问题只有在第 1、2 都成立时才有意义。

## 1. 范围

**做**：

- `ev` CLI + SQLite（[事件规格 §7](event-spec.md) 的 schema）
- 一个夜间系统巡检（systemd timer → spool），只产生 `system.*` 事件
- 每日 digest 纯文本（`ev digest`），存文件，不做推送

**不做**（这一周内一条都不要碰）：

- 常驻 `eventd` 的常驻判定；判定先用 `ev judge --rule` 手动跑
- MQTT、HA、墨水屏、DS-Bot、手机
- 任何 LLM 参与判定
- Web UI、图表、统计看板

**唯一例外**：允许写一个 30 行的 `nightly-scan.sh` 进 cron，把磁盘、服务状态、日志错误数写成 spool 文件。它的作用不是自动化，而是验证"外部写入的机器事件"和"人手记的事件"能不能落在同一张表里而不打架。

## 2. 每天三分钟

| 时刻 | 动作 | 时长 |
|---|---|---|
| 早上 | 看昨日 digest，把逾期项逐条 `ack` / `close` / `defer` | 2 min |
| 随时 | 发生值得记的事：`ev add -k ... -s ...`，payload 一句话 | 10 s/条 |
| 晚上 | 补记白天漏掉的；跑 `ev digest --day` 存档 | 1 min |

**记什么**：凡是你会在第二天想起来"哦还有这件事"的东西。判断标准是事后是否可能遗漏，不是事情大小。

## 3. 首批事件类型

只允许这些，不够就加，但**先加 kind 再记**（[事件规格 §1.3](event-spec.md)）。一周后看哪几个从未出现，就删掉。

| kind | 何时产生 | 典型处置 |
|---|---|---|
| `study.homework.due` | 作业有截止 | `defer` 到当天，`close` 提交后 |
| `study.class.attendance` | 需要签到的课 | `close` 签到后 |
| `life.errand.pending` | 快递、缴费、取物 | `close` 办完 |
| `life.health.checkup` | 体检、复诊、用药 | `defer` |
| `work.repo.ci_failed` | 巡检发现 | `escalated` 让人看 |
| `work.deadline.approaching` | 自定节点 | `defer` |
| `system.disk.pressure` | 巡检 | `human` |
| `system.service.failed` | 巡检 | `human` |
| `meta.capture.forgot` | 事后才想起的事 | `close` 并记"本应更早" |
| `meta.idea.spark` | 想法、可做的东西 | `defer` 到周末 |

`meta.capture.forgot` 是这套实验最重要的一个 kind：它记录的是**系统漏掉的东西**，是"未匹配率"的人工版本。

首批里只有 `study.homework.due`、`life.errand.pending` 带明确截止，其余都靠 `defer` 指定时间。**每条 `add` 都要顺手填 `valid_until`**（作业截止后、快递签收后的一天），否则一周后账里会堆满已经没意义却没关掉的事——这是最常见的失败方式，而且它让人不再相信账。

## 4. 一周后看什么

不看数量，看四件事：

| 观察 | 结论 | 行动 |
|---|---|---|
| 有 ≥ 3 条 `meta.capture.forgot` | 模型成立，但触发点选错了 | 把漏掉的那类转成自动源（进 P1） |
| 持续 7 天都有记录 | 可坚持 | 进 P1 |
| 第 3 天起就不记了 | 粒度太细 | 砍到 3 个 kind 重试一周 |
| 记了但从不回看 | 账没进入日常 | 问题在呈现，不在采集；先解决"看什么" |

**放弃标准**（写下来是为了防止自欺）：砍到 3 个 kind 再试一周仍不记，说明这套制度对当前生活强度过重，应当停在"只做巡检 + 提醒"，不做全量账。**这不是失败，是把设计收缩到真实需求**。

## 5. P0 之后

只有 P0 通过才继续，按 [架构总览 §15](architecture.md) 的顺序：

| 阶段 | 进入条件 | 关键新增 |
|---|---|---|
| P1 常驻入账 | P0 记满一周 | `eventd`、两个真实源（学习通通知、系统巡检）、规则 `lint`、`ev replay` |
| P2 派发闭环 | P1 的未匹配队列 < 20% | `agent` handler 接 Orca、回执记录、超时转 deferred |
| P3 设备面 | `home` 域有 ≥ 5 个稳定 kind | MQTT 桥、墨水屏日卡、HA 只留安全兜底 |
| P4 反哺 | P2 落定率可统计 | 周报、规则候选、人工合并 |

每个阶段都可以停在原地：账不动、数据不迁、回退就是停服务。

## 6. 与旧设计的差异

P0 之前仓库里的"实施顺序"散在各个域文档（宿舍、墨水屏、书籍流水线），彼此独立、没有总序。本文明确定义了一条主轴：

```
记账能力 → 常驻入账 → 派发闭环 → 设备面 → 反哺
```

各域文档的实施顺序（比如宿舍的"先买 ESL 再上传感"）**保持有效，但要挂在这条主轴之后**：没有账与规则包，宿舍场景只能停在 HA 自动化，"agent 增强"那部分做不了。

## 未决项

- P0 是否需要一个最小的 `ev review`（随机抽 5 条问"当时处理对了吗"），还是靠周末人工翻账。
- 夜间巡检的范围（只做摘要还是也做趋势对比），取决于 P3 之前是否需要磁盘增长分析。
- 是否把 P0 的手工记录开放给手机（只读 + 添加），还是坚持只能在终端记。倾向后者：P0 的目的是验证制度，输入成本高正好能暴露粒度问题。
