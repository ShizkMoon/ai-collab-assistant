# 设计原则

## 约束先行

让环境本身承载约定（目录结构、规则文件、服务单元），而不是依赖每次会话里的口头指令。Agent 读到什么规则，就应该等于系统真正的边界。

## 单一来源

同一事实只在一个地方维护，其余入口用链接、软链或生成物指过去。需要"同一份内容多处生效"时，选引用而不是复制。

## 作用域分层

- 全局层：适用于所有工作的机器级约定（如全局 `AGENTS.md`）。
- 域层：某一棵目录树的约定（如数据盘自己的 `AGENTS.md`）。
- 项目层：单个作品的 `AGENTS.md` / `.devin/` 规则。

上层不该重复下层细节；下层可以收紧，不推翻上层。

## 可回退

每个自动化、迁移、兼容补丁都附带回退路径；不可逆操作必须显式确认。

## 事件优先

凡是要在"人不在场"时发生的事——传感器触发、定时、平台来消息、系统异常——都必须先成为事件再谈处理。以任务或会话为单位的设计会漏掉这些事：它们的起点不是人的一句话。

推论：任何新能力先回答"它的输入是哪种事件"，再回答"它怎么执行"。只回答后者的，就是脚本，不是制度的一部分。

## 记录先于记忆

"发生过"和"处理过"都要留下能回看的痕迹：一句话结论，加上可选的引用（提交、命令、路径、消息 id）。目的是三个月后还能回答"当时凭什么这么判断"，不是证明执行者没撒谎。

## 校验只放在基座

校验检查**不变量**——账只有一份、状态按序前进、事件不可改、去重键唯一。这些是结构约束，写进 schema 和状态机后不再需要人操心。

不在执行层校验：机器只能查形式（有没有回执、退出码是不是 0），形式对而结果错是常态；更糟的是，一旦落定需要"证明"，执行者会生产能过关的材料而不是正确的结果。**正确性只有人知道，能自动化的是存在性与可追溯性。**

推论：自动化越深，越需要**外部观察点**（进展是否真的在变），而不是更严的门禁。自己去报进展的流程在失控时仍然只报进展。

元规则与五条不变量的完整表述见 [架构总览](architecture.md) §1；可校验的契约见 [事件规格](event-spec.md)。
