# 设计原则

以下原则约束全仓的设计取向，具体实现机制见各专题文档。

## 功能优先，够用即止

先保证系统日常可用，再逐步补充规则。不预先设计复杂的抽象层、校验层或权限层；当某类问题实际发生后，再针对性增加处理规则。

## 优先复用开源方案

每项能力优先在 [开源复用清单](open-source-reuse.md) 中寻找成熟项目。现成工具可直接使用，功能相近的加一层薄封装；仅在社区无可用方案时才自建，并保持模块小巧可替换。自建模块需说明缺乏现成方案的具体原因。

## 事件驱动

所有无需人工在场即可触发的操作（如传感器状态变化、定时任务、外部平台通知、系统异常），均先转化为标准任务记录，再进入后续派发与执行流程。

## 反馈闭环

每次人工返工、操作撤销或手动补救都作为优化信号记录下来。规则、能力与提示词的调整统一通过 [提案库](proposals/README.md) 评审和影子测试后上线，避免 Agent 在运行中自行修改配置。

## 任务记录优先于派生记忆

所有执行过的任务均在任务库中留存一句话摘要。偏好、人物设定与知识库均从任务记录和原始文档中提炼派生，不维护平行的第二套任务状态源。

## 单一数据源（Single Source of Truth）

同一类事实只在单一位置维护，其余入口通过链接、符号链接或构建产物引用。各类状态的权威存储位置见 [总体架构设计 §9](architecture-north-star.md#9-状态归属表)。

## 可回滚

操作系统配置通过 NixOS generation 回滚，能力实现通过 Nix 包版本回滚，可逆操作提供默认 5 分钟的撤销窗口。全系统仅对付款、删除、对外发布三类操作设置人工确认点。

## 故障降级预案

工作站、N100、路由器、外网或云端模型任一故障域失效时，系统按预设降级策略切换。架构上优先保障本地闭环可用，云端能力作为增强层。详见 [总体架构设计 §6](architecture-north-star.md#6-故障域与降级策略)。

## 显式声明自治等级

每项能力在 TOML 配置中声明 L0–L4 自治等级上限，运行时不得越界。涉及付款、删除、对外发布的操作上限固定为 L1。详见 [总体架构设计 §5](architecture-north-star.md#5-自治等级)。

## 规则作用域分层

- 全局层：机器级通用约定（全局 `AGENTS.md`）。
- 域层：特定目录树的共享约定。
- 项目层：单个仓库的 `AGENTS.md` 或 `.devin/` 规则配置。
