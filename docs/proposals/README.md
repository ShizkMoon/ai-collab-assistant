# 提案库（Proposals）

新增或调整规则、能力、场景与提示词时，统一先在 `docs/proposals/` 下建立提案文件，经旁路验证后再合入线上配置。

## 文件命名与内容要求

提案文件命名为 `docs/proposals/NNNN-slug.md`，编号递增且不重复使用，编写格式参考 [提案模板](TEMPLATE.md)。

每份提案需包含以下四项内容：

1. **支撑证据**：列出触发该提案的历史任务 UUID、人工返工记录或周报统计链接。
2. **配置草案**：给出可直接评审的规则 TOML、能力 TOML、场景 TOML 或提示词正文。
3. **影响范围**：说明是新增还是替换，以及会影响哪些既有 `kind`。
4. **预期收益**：说明预计每周可减少多少次手动操作或返工；无法量化实际收益的提案不进入影子测试。

## 提案生命周期

| 状态 | 含义说明 | 状态流转条件 |
|---|---|---|
| `proposed` | 已具备支撑证据与配置草案 | 人工审阅确认后进入下一阶段 |
| `shadow` | 在真实触发下旁路运行，输出仅写入隔离目录 | 影子测试默认持续 7 天或累计满 20 个样本 |
| `accepted` | 正式启用并合入能力目录或规则表 | 影子测试期采纳率 > 60% 且无异常回退 |
| `rejected` | 放弃采用 | 支撑证据不足或影子测试效果不达标 |
| `superseded` | 被后续新提案替代 | 在元数据中指向新提案编号 |

状态记录在文件头部的 YAML frontmatter 中：

```yaml
---
status: shadow
opened: 2026-11-01
shadow_since: 2026-11-03
evidence: ["3f2a…", "9c11…"]
---
```

## 提案来源

| 来源 | 触发条件 | 生成方式 |
|---|---|---|
| 周度复盘 | 同类任务累计手动处理 ≥ 3 次 | 序列模式挖掘（PrefixSpan）+ 模板生成 |
| 返工与撤销统计 | 同一类任务累计返工 ≥ 2 次 | 提取失败原因，生成规则或提示词修正草案 |
| 日常对话 | 用户明确要求"以后这类事都按这个方式处理" | 入口 Agent 直接根据当前操作生成草案 |
| 下线评估 | 某项能力连续 8 周零调用或连续失败 | 自动生成下线提案供人工确认 |

## 边界说明

- 提案不会自动合入线上能力目录，启用需经过显式的状态修改与 Git 提交。
- 提案文件属于设计期配置文档，不混入 Taskwarrior 运行时任务库。
