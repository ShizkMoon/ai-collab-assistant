# 多 agent 协作

## 规则入口统一

不同 agent 读取的规则文件名不同（`AGENTS.md` / `CLAUDE.md` / `GEMINI.md` / 各自配置目录下的全局文件）。用软链把它们指向同一份文件，保证所有 agent 共享同一套约定，修改只改一处。

## 上下文的分层加载

- always-on 规则：放全局与目录级 `AGENTS.md`，保持精简，细节链接到专门文档。
- 触发式规则：按主题拆分，需要时才加载，避免规则膨胀稀释注意力。
- 长期资料：沉淀到知识目录，规则文件只放指针。

## 任务边界

- 常驻服务（守护进程类工具）用系统服务管理生命周期，与交互会话解耦。
- 每个 agent 的会话、缓存、凭证保留在其原生位置；跨 agent 共享的只有规则与文档，不共享状态。
- 破坏性操作、凭据写入、对外发布统一要求显式指令。

## 协作模式

共同原则：Agent 之间通过账（Taskwarrior 的 `thread` / `parent`）交接，不直接对话；产物都写成文件，交接时只传路径。

| 模式 | 用在哪 | 说明 |
|---|---|---|
| 流水线 | 播客、视频 | 转写 → 剪辑 → 字幕 → 封面，每一步都可以换 provider |
| 并行分节 | 长文、调研 | 主编拆大纲 → 各节并行写 → 合稿 |
| 作者 + 审稿 | 写作、代码 | 用不同厂商的模型（比如 DeepSeek 写、Qwen 审），减少同源错误 |
| 主编 / 制片 | 复杂任务 | 一个主 Agent 维护 thread 进度，其他 Agent 只干活 |
| 竞稿 | 封面、标题、配乐 | 多个 provider 各出一版，你挑一个，挑选结果就是偏好数据 |

模型统一经 LiteLLM 网关调用，所以"换一个厂商的模型来审稿"只是改一个模型名。

### 写作工作室（示例）
```
你：写一篇 NixOS + Plasma 迁移记录
主编 → 出大纲（卡片给你确认）
     → 三个写手并行写各节（各自用 info.recall 从账里找相关记录）
     → 审稿（换一个模型）→ 合稿 → 公众号排版
     → 卡片："初稿好了，3200 字，[看] [改] [发布]"   ← 发布是确认点
```

### 视频工作室（示例）
```
你：把周末爬山的素材剪个 vlog
制片 → 筛选素材（选出高光片段）→ 粗剪（Remotion / ffmpeg）
     → 调用 work.music.compose 配乐（子事项，ACE-Step）
     → 字幕（FunASR）→ 封面竞稿 3 张
     → 卡片："成片 3:12，[看] [换配乐] [选封面] [投稿草稿]"
```
