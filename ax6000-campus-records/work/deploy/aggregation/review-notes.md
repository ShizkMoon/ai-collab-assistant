# 三路聚合下载独立复核

本轮目标是电脑通过当前路由器、多连接下载达到稳定 900 Mbps 应用净载荷。本文只分析本地保存的资料，不连接设备，不修改公共脚本和文档。新 result-summary.json 尚未生成，以下是主线实验的判据，不是新实测结论。

## 旧证据为什么不足

- frontier/three-download-flow-evidence.json 保存的 768 MiB 批次完整、约 581.55 Mbps，但稳态窗口仅 9.078 秒。16 条 PC 下载内层 ESTABLISHED 的 mark 为 6／5／5；采集没有对应固定下载源的 WAN 外层 ESTABLISHED。负载前的 4 条小 TIME_WAIT 不能归入大下载，三种 mark 不能代替实际出口发包和回包。
- frontier/three-small-flow-acceptance.json 的 3 个 1 MiB 限速请求全部 HTTP 206 完成；UA3F PID＋socket inode＋original／reply tuple 实际确认了主出口和第三出口的若干外连。all_three_exits_observed=false，没有第二出口，也没有逐个 PC curl 到外连的映射；来源 DNS 会变，外连分别出现多个远端 IP。这只能证明所观测短流的进程归属和出口，不能证明三路大下载或 900 Mbps。
- next/cake-comparison.json 的 off／split-gso 都固定相同来源 IP、请求完整，分别为 232.81／263.80 Mbps；三出口同源覆盖不足，均 inconclusive。no-split-gso 的 803,143,174 字节不完整，不能和完整 805,306,368 字节批次作吞吐优劣结论。旧 581.55 Mbps 没有同期控制，不能用于 CAKE 因果比较。

## 旧脚本的三路适用边界

root/microsoft_throughput.py 第 32、109～110 行只读 wan／eswan2，estimated_main=physical_wan-eswan2；在三路时会把 eswan3 计入所谓主路。不能沿用这份字段来声明三路贡献。该脚本只保存 curl 完成后的汇总，不能从完成顺序或总平均反推稳定窗口；总任务数不等于同时活跃数。完成判定只查 exit=0、HTTP 206 和精确 size_download，未验证 Content-Range 的起止、对象总长或版本标识。

root/summarize_download_flows.py 第 19～28 行把 original 源 10.207.*、固定目的、mark 作为候选，缺少 UA3F inode／PID、ESTABLISHED 状态及 NAT reply 目的实际出口验证。第 38 行只汇总 WAN 1／2 的字节，不包含 3；使用连接最后 reply bytes 是累计计数，不是负载窗口严格字节增量。第 37 行的物理 WAN interval Mbps 包括协议开销和无关流量，不能替代 PC 应用净载荷 Mbps。这些是旧双路候选工具的边界，不应直接作为新三路验收器。

## 最小充分证据标准

1. **先固定 900 的测量路径与口径。** 必须是 Windows PC 经家庭路由器的下载，绕过 PC 本地代理／VPN接管，并核实实际 WLAN／有线接口。吞吐为完成的应用字节 × 8 ÷ PC 的真实批次单调时钟持续时间 ÷ 1,000,000，单位 Mbps。路由器自己 curl、LAN RAM 下载、无线协商速率、各流 speed_download 相加、物理 RX 瞬时峰值都不能替代这一结果。
2. **控制限速。** 当前共享 IFB CAKE 下载上限为 650 Mbit；若三路 PC 接收都经过该队列，不能在维持这一配置时验证稳定 900 Mbps。单／双／三组必须处于相同明确 CAKE 状态和参数，记录运行 qdisc／IFB、服务与 watcher 状态及设置时间。临时停止或提高上限后的数据要另列 epoch；最终恢复读回。不能拿一组 CAKE off 和另一组 650 Mbit on 比较聚合增益。
3. **相同来源和任务。** 三组固定 URL／对象版本、固定 remote IPv4／port、HTTP 版本、相同 Range 起止集合、字节总量、每片大小、实际最多活跃 worker、总请求数和超时；核实每请求 HTTP 206、Content-Range、精确字节与退出码。redirect、新远端 IP、重试、分片改变必须显示，不能混入同一可比组。来源对象范围和请求集合不同，只能各自报告吞吐。
4. **明确 epoch。** 每组前后读回有效 MWAN／UA3F OUTPUT 策略、成员和权重，当前 DHCP IP／device、boot ID、UA3F／认证 PID＋starttime、CAKE、WLAN 链接、负载前基线；记录 PC 计时与路由器采样窗口的对应边界。策略切换后等旧连接退出再只使用新连接，不能将旧 conntrack、TIME_WAIT、既有 keep-alive 跨组混算。实验过程中发生 DHCP、认证、进程或成员状态变化则另列 epoch，不作完全控制比较。
5. **证明本轮实际出口。** 在负载窗内捕获 UA3F PID＋socket inode 的固定来源 ESTABLISHED，匹配 conntrack original tuple 后，用 NAT reply dst 对照该 epoch 的各 WAN 地址确定实际出口；同时取得该连接的接收 byte 增量或等价的按 tuple 包记录。每个目标出口必须在重叠负载时段有真实收到下载数据的较大新流，不能只出现 SYN／少量握手／负载前 TIME_WAIT。计数按唯一双向 tuple＋epoch 去重，mark 只作策略佐证。
6. **聚合证明可以少于逐 curl 全映射，但限制要明确。** 若已隔离同一来源的大下载负载、无同源背景流，且各出口的大流归属、时间重叠和接收增量明确，可以证明该批次三出口同时下载；无需为此强制逐片解释所有 curl。不能据此宣称每个 curl 的固定出口、三路字节各占三分之一，或未经采集的所有窗口均覆盖。物理 wan 是 macvlan 下层，不能与 eswan2／eswan3 RX 相加；主路差额估算须至少扣除两 macvlan，并仍标为粗略差额，不代替逐流统计。
7. **区分达到与稳定。** 单个完整批次平均 ≥900 Mbps 只能证明该批次达到。建议将本轮有界“稳定达到”明确定义为至少 3 个完整三路批次，分别具有不少于 30 秒的有效负载窗口，记录应用累计字节的 5 秒窗口速率、均值和低分位，无失败、成员掉线或重认证影响；持续窗口内也需达到所声明阈值。达不到时报告实际窗口与速度，不把峰值、短窗平均或单次最好结果写成稳定。这个定义不证明数日运行、全部下载站点或所有终端。
8. **单／双／三组的比较。** 匹配三组只允许出口集合改变；最好用同窗交错或回到前一组作漂移控制。单一顺序的 1→2→3 各一次仍受 CDN／时段影响，可证明各次完成和对应实际出口，不能将比例全部归因于通道数。即使三路完整批次达到 900，稳定收益与通道数因果仍分别核对。
