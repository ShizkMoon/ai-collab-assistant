# Wi-Fi 约束下的已保存样本分析

**目前不能把电脑低速判定为“防检测导致”。** 固定目标的路由器本机 SOCKS→UA3F 已完整达到 902.30 Mbps，随后裸三出口重复为 908.67 Mbps。UA3F 路径确有 CPU 成本，但这组证据排除了“现有 UA3F 路径本身必然只能跑 200～350 Mbps”的说法。电脑全路径低速仍有多个叠加因素：实际 CDN 变化、额外 TCP 转接与无线收发共同带来的处理成本，以及部分批次的流完成尾部。无线重试、单核压力和这些因素各自造成多少吞吐损失，当前数据不能给出百分比分摊。

本分析只读已保存 JSON／采样代码与 PC 资料，使用本地 Python 重算；没有 SSH、网络请求、浏览器或设备修改。PC 必须保持 Wi-Fi，没有提出有线验证、换硬件或刷固件。

## 证据权重

| 候选解释 | 当前支持力度 | 证据与边界 |
| --- | --- | --- |
| 实际目标／CDN／到目标的路径不同 | 强，已确认是对照混杂变量 | PC 内层 resolve 未固定外层；一批实际外层为 `120.226.112.10`。裸三出口固定 `171.108.211.12` 为 921.67／908.67，固定 `111.2.112.12` 只有 146.25 Mbps 且 CPU 有余量。可以确认目标变化影响比较，不能由此唯一归因 CDN 服务器限速，或把低速全部算给源站 |
| 完整 PC 路径的 CPU／softirq 成本 | 强，部分批次有持续饱和信号 | PC 352.73 Mbps 的 CPU2 平均 busy 96.4%、softirq 89.9%；14 个观测区间中 12 个有任一核心 ≥90%。PC 213.50 组也有 10／21 个 ≥90% 区间。PC 169.60 组却无 ≥90% 区间，说明处理饱和不能解释所有低速批次 |
| UA3F 与防检测功能自身形成低速硬上限 | 不支持该强结论 | 固定本机 UA3F 902.30 Mbps，12 个固定目标外连均观测并有增长。该组未做“关闭 UA 重写”的因果对照，不能量化重写、复制、socket 和内核收发各自成本；也不能把整个 OpenClash→UA3F→无线链的开销等同于防检测功能开销 |
| 上游检测电脑特征后主动限速 | 没有直接证据 | 当前文件没有检测命中、服务端限速通知、同端点且仅改变指纹的对照或对应校园策略证据。不能由“电脑慢、本机快”直接推断已经被识别并限速，也不能用本机 UA3F 的快样本证明所有识别策略都不存在 |
| Wi-Fi 空口丢包／重传是主要根因 | 未确认 | LAN 窗口有前后 `iw` 增量；公网 PC 采样没有 `iw`、airtime 或 survey，所以缺同一负载窗的无线计数。不得将预检累计 retries／failed 或 LAN 窗口增量移作公网 PC 窗口丢包证据 |
| 各流速率不均、最后几流拖尾 | 部分支持 | PC 162／170 组各流 duration 分散明显；352.73 组 duration 很集中，尾部不能解释该组差距。缺每请求绝对开始／结束时间，当前只能计算 duration 分散指标，不能精确重建动态活跃连接数 |
| CAKE 650 是当前数字上限 | 条件确定，但不是全部低速的解释 | 经过 IFB 的持续大包应用速率不能达到 900；PC 当前多组仅 162～353，远低于 650 的大包净应用上限。开关组实际外层目标没有固定且结果方向不一致，不能确定队列因果收益或损失 |

“强”表示样本中有清楚观察，不是根因概率或损失份额。关闭卸载、重复进入用户态代理与逐包处理存在成本上的合理性，但没有对应对照或函数级采样，不能把这些尚未分离的成本统称为已证实防检测损失。

## 重算的 CPU 和内核收发数据

每个组的 `/proc/PID/stat` 增量用同期整机四核 `/proc/stat` 前 8 项总增量作分母；25% 整机 CPU 相当于占满一核的计算量。进程列是整个进程的 user＋system 计时，不能代表某个线程、锁、函数或加密算法。

| 完整批次 | 应用 Mbps | 整机 busy／softirq | UA3F user／system，占整机 | clash user／system，占整机 |
| --- | ---: | --- | --- | --- |
| 裸三出口首次 | 921.67 | 36.1%／7.7% | 0.12%／0.12% | 0.34%／0.19% |
| 本机 SOCKS→UA3F，固定目标 | 902.30 | 57.5%／13.4% | 1.90%／10.40% | 0.33%／0.12% |
| 裸三出口随后重复 | 908.67 | 33.7%／6.8% | 0.03%／0.03% | 0.15%／0.15% |
| PC CAKE 650，第一个窗口 | 162.44 | 50.8%／16.6% | 1.59%／7.28% | 1.81%／5.04% |
| PC CAKE off，第一个窗口 | 169.60 | 53.9%／15.2% | 1.90%／6.95% | 2.13%／6.33% |
| PC CAKE 650，第二个窗口 | 352.73 | 83.7%／34.1% | 2.31%／11.01% | 2.69%／8.24% |
| PC CAKE off，第二个窗口 | 254.92 | 61.2%／19.5% | 2.06%／7.54% | 2.45%／7.31% |
| PC CAKE 650，实际外层已捕获 | 213.50 | 67.6%／24.8% | 2.26%／8.94% | 3.39%／7.86% |

本机 UA3F 的吞吐仅比紧邻裸重复低约 0.7%，整机 busy 却高 23.8 个百分点，显示额外转接确实消耗资源；这不是独立关闭／开启 UA 重写的试验。PC 同时包含 clash、UA3F、更多 TCP leg 和 AP 发射，不能从表中直接相减得出“无线成本”或“防检测成本”。进程 CPU 与 softirq 是不同统计视角，不将各列相加或按倍率预测可用吞吐。

所有这些聚合批次的 `softnet_stat` 第 2 列 dropped 前后增量均为 **0**。第 3 列 time_squeeze 总增量分别为：裸首次 2、本机 UA3F 21、裸重复 2；PC 162／170／353／255／214 组为 0／12／0／103／0。time_squeeze 表示处理预算耗尽的次数，不是丢包。CPU2 的软网络处理事件增量在 PC 352.73／213.50 组约 191／197 万，而裸三出口首次／重复约 70／70 万；这是内核处理计数，受多个 TCP leg、GRO／分段及背景流量影响，不能称为线上的实际报文数或重传倍数。

PC 213.50 组同期全局 `Tcp:RetransSegs` 增量为 **17,469**，其他 PC 组为 39～202。可以记录该窗路由器本机 TCP 重传较多；它涵盖代理内外腿与背景流量，缺每 socket 的 TCP_INFO／重传位置，不能将 17,469 全算成 Wi-Fi 丢包。物理 WAN／应用字节比约 1.071，也不能据此直接换算损包率。该组 `Ip:ForwDatagrams` 增量为 407、`Ip:InDelivers` 为 922,050，说明本机终止／重新建立 TCP 的递送处理很多；不能拿纯内核 FORWARD／硬件 NAT 的吞吐模型替代当前代理路径。

采样也有测量边界：CPU 用前后 snapshot 范围，约为负载墙钟加 0.4～1.6 秒；单次完整 snapshot 的中位时间，裸组约 0.43～0.52 秒，PC 约 0.45～0.69 秒。本机 UA3F 与紧邻裸重复的 snapshot 总跨度同为约 8.5 秒，但实际负载各约 7.1 秒。PC 捕获的 TCP／conntrack 数据更多，采样自身也是额外工作，不能把所有 CPU 都视为业务线程净成本。

## LAN 的无线前后增量：能说什么

当前 `lan-current.json` 三批均完整下载 512 MiB，应用速率为 **567.06／600.71／605.33 Mbps**。CPU 平均 busy 为 **19.3%／23.1%／26.5%**，最高核的全窗均值约 **42.6%／52.6%／50.4%**，没有全窗 CPU 饱和证据；没有逐秒 CPU 或 uhttpd 进程采样，仍不能排除短时、单服务或客户端处理限制。因此 605 不是已证实 Wi-Fi 硬件硬上限。

与这三批字节量一致的大流量 STA（当前文件没有同步 IP→MAC 映射，先不把其身份视为额外验证）得到以下前后差：

| LAN 批次 | tx bytes 增量 | tx packets 增量 | tx retries 增量 | tx failed 增量 | rx drop misc 增量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 worker | 556,772,938 | 368,126 | 928 | 928 | 0 |
| 2 workers | 557,001,635 | 368,363 | 782 | 782 | 0 |
| 2 workers 重复 | 557,019,757 | 368,283 | 1,049 | 1,054 | 0 |

这些是本次 LAN 窗口的差值，前后 connected time 连续，没有观察到计数重置。不能用驱动这几个字段直接计算 TCP 丢包率，也不能仅凭它们证明空口是主要瓶颈。signal 前后约 −38～−40 dBm；大多数边界快照的 tx PHY 为 2401.9 Mbit/s／160 MHz／2 NSS。第二批结束一次显示 6.0 Mbit/s，它可能是低负载时最后一次低速帧；边界快照不能代表整批数据发射速率，不应据此宣称负载时持续跌到 6 Mbps。

公网 PC 的 `samples.raw` 只有 CPU、NET、PIDS、PROC、SOCKETS、TCP、CT、MEM、SOFTNET、SNMP、QDISC。**没有同步 station dump、channel survey、每秒实际 MCS／NSS、airtime、AP TX 队列／重试增量**，也没有 PC 网卡 errors／discards、每核 CPU 或 per-socket 重传。预检中的约 14.7 万 tx retries／tx failed 是累计值，不能作为这五个公网批次的增量。

已保存 PC 清理验收记录 Wi-Fi IP `192.168.31.171/24`、默认路由经 `192.168.31.1`、ESurfingClient 和 watchdog 进程为 0。这不证明负载窗没有其他 CPU／无线使用者。采样请求为 `curl.exe --noproxy '*'`、输出 NUL，避开普通系统 HTTP 代理和磁盘写入；透明路由器代理仍存在。历史 PC Clash 配置记录不能替代当前负载窗进程、TUN、网卡或 socket 读回，不把旧配置当作本轮低速解释。

## 尾部与 CDN 的作用

每请求保存 `time_total`，没有绝对 started／ended；下面用各流 duration 的最大值减排序第 9／12 个 duration，作为尾部分散代理指标，不称为准确的“75% 请求完成后墙钟”。

| 批次 | 最快／中位／第 9／最慢 duration，秒 | duration 分散尾部／全批时间 |
| --- | --- | --- |
| PC 162.44 | 8.823／20.991／32.140／39.578 | 7.439 秒／18.8% |
| PC 169.60 | 23.213／30.212／32.128／37.916 | 5.788 秒／15.2% |
| PC 352.73 | 16.861／17.793／18.096／18.184 | 0.088 秒／0.5% |
| PC 254.92 | 1.985／20.866／22.214／25.180 | 2.966 秒／11.7% |
| PC 213.50 | 21.013／23.827／26.355／30.020 | 3.665 秒／12.1% |
| 裸三路首次／重复 | 最慢 6.967／7.047 | 0.453／0.487 秒，约 6.5%／6.9% |
| 裸三路另一端点 146.25 | 18.249／23.625／30.998／44.025 | 13.027 秒／29.6% |

尾部使部分完整批次平均下降，不能解释没有明显尾部的 PC 352.73 与裸三路 900 的差距。PC 162.44 中最快流明显早结束，也不能由 duration 就确定某个出口慢：缺每请求与实际外层的逐条映射。实际外层域名重新解析已经观察到，必须固定并读回外层目标后才可进行 CPU／无线因果比较。

## 在 Wi-Fi 约束下的最小精确验收

不改电脑连接方式、位置、信道、带宽或认证。主线只需要一个**确实固定外层 CDN 的完整 Wi-Fi PC 批次**，与紧邻固定目标本机 UA3F 批次配对；保留现有防检测、TTL、认证与三出口策略。内层 `--resolve` 不作为固定证明，实际 UA3F socket→conntrack 的目的必须为指定地址。具体临时目标固定方法由主线独占实现并回退，不能为固定目标无差别改全局解析或停用防检测。

同步保存的最小补充字段是：PC IP→STA MAC 映射；公网负载前／中／后的同 STA `iw` 计数、连接 uptime、tx bytes／packets／retry／failed、signal／MCS／NSS／airtime；路由器各核 CPU 与 `/proc/softirqs`、softnet、UA3F／clash 进程 jiffies；PC 网卡 bytes／errors／discards、每核 CPU；每 curl 的绝对 started／ended。若全局重传再次明显升高，再读相关 socket 的 TCP_INFO 区分电脑内层、clash↔UA3F 和外层；不需要先新增大量逐包捕获或安装分析工具。

判据：

- 固定目标的本机 UA3F 仍快，Wi-Fi PC 明显慢且 CPU2 NET_RX／softirq 持续接近满载，无线增量没有与低速对应的异常时，支持完整 PC 代理／收发处理路径成本；仍不把它单独命名为 UA 重写损失。
- 固定目标的 PC 低速对应明显的当窗无线重试／failed 增量、airtime 或 MCS 变化，而路由器及 PC CPU 有余量时，才优先支持无线链路限制；计数须与完整字节、连接未重置、背景流量及时间窗一致。
- 固定目标后 CPU／无线没有相应限制，而尾部集中在少数已映射外层连接，则定位流分配／该路径波动。若本机固定 UA3F 也同步下降，先保留源／校园到源路径因素，不归因无线。
- 要验收稳定 900，临时整形状态必须允许超过 900，完整净字节／墙钟、真实三出口覆盖与至少 10 秒稳态须一并通过并重复。当前 650 队列不允许该目标；当前 768 MiB 在 900 下仅约 7 秒，完整短窗成功不等于稳态验收。此处提出的是判据，没有执行新负载或承诺调整队列后就能通过。
