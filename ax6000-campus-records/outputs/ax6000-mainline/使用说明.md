路由器已永久安装 OpenWrt，当前运行四路校园网认证、MWAN 分流、四出口 IPv4 TTL64 与 DNS 广告过滤。2026-10-27 起代理已移出路由器：OpenClash、Ninja Connector、UA3F、smartdns、Ruby 及 iptables 依赖已卸载，overlay 从 83% 降到 15%。本机 NixOS 运行 Ninja `ab32ad2d`，混合端口 `127.0.0.1:7890`，固定香港 02；systemd 用户服务已 enable，`Linger=yes`，配置为开机自动启动（未做整机重启实测）；Firefox 与 CLI 已实际走该代理。5 GHz 为 HE160，WED 已挂接；CAKE 服务当前 disabled，BBRv1 默认保留；四路与清理后的冷启动、电脑稳定 900 Mbps 仍未验证。

**当前状态以 2026-10-27 读回为准。** 四个认证实例 PID 12275／12276／12277／12278 均在运行，`wan`／`wan2`／`wan3`／`wan4` 全部 online，四条出口分别取得 HTTP 204；本机代理 Google 204、GitHub 200、Cloudflare 约 22.5 MB/s，出口 `188.253.112.163`（香港），百度在 Ninja 日志中为 `DIRECT`。路由器已无 OpenClash／UA3F／smartdns 进程和 1080／7874／7890 监听。

## 下载分流与 Edge

> 2026-10-30 更新：Ninja 已回滚到路由器，OpenClash `0.48.002` + Connector `1.1.0-r4` + 固定核心 `ab32ad2d` 正在运行，LAN 透明代理生效（本机实测出口香港）。以下 OpenClash 下载规则与 Edge／PAC 段落重新适用；**UA3F 未装回**，`enable_ua3f_tcp` 已改为 `false`，所以「🎯 全球直连」的 TCP 直接走 MWAN 四路直连，不再经 `127.0.0.1:1080`。smartdns 未装回，旧选项里的 `127.0.0.1:6054/6055` 已改指向 `223.5.5.5`／`119.29.29.29`。本次未重启路由器，冷启动与吞吐均未复测；回滚细节见 [Ninja 回滚记录](../../work/deploy/ninja-rollback-20261030/README.md)。

OpenClash 已增加 11 条下载域名规则，保持原匹配范围：`steamcontent.com` 是后缀规则；`steampipe.akamaized.net`、`dl.steam.clngaa.com`、`dl.steam.ksyna.com`、`st.dl.eccdnx.com`、`xz.pphimalayanrt.com`、`steampipe.steamcontent.tnkjmec.com`、`steampowered.com.8686c.com`、`steamstatic.com.8686c.com`、`wmsjsteam.com` 是精确域名；微软仅增加精确域名 `dl.delivery.mp.microsoft.com`。没有把全部 Microsoft 服务或 Steam 商店／社区改为同一策略。

匹配的 TCP 下载仍经路由器 OpenClash→UA3F→实际 WAN。专用 `ua3f_bal` 在 UA3F 新建外连时轮换出口，其他普通 `balanced` 流量保留随机选择。轮换的是独立连接，不是一个连接内的字节；现有连接继续使用已经选定的出口。Windows PAC 在家返回 `DIRECT` 后，仍会经过路由器的上述规则。

Edge 并行下载开关已开启并读回，但是否产生多个独立连接取决于响应的 Range、校验信息、文件大小、协议及浏览器的运行策略。多次请求还可能复用同一个传输连接；开启该开关不能保证固定连接数、均分字节或达到 700 Mbps。需要比较实际 Edge 下载时，应保持同一下载源、同一网络与相同本地代理状态，并观察连接和完成时间。后述 8／16／32 路测试使用独立 curl 连接，不能等同于 Edge 的默认下载行为。[Chromium 并行下载参数](https://github.com/chromium/chromium/blob/155.0.8059.9/components/download/internal/common/parallel_download_utils.cc)、[并行下载触发条件](https://github.com/chromium/chromium/blob/155.0.8059.9/components/download/internal/common/download_job_factory.cc)

Edge 155 当前没有 `QuicAllowed`／`EncryptedClientHelloEnabled` 禁用策略，未设置时默认允许相应协商。本轮尝试将当前用户两项策略明确写为 1，Windows 拒绝创建 HKCU 策略分支，实际没有新增策略。指定 `crypto.cloudflare.com` 新连接取得 HTTP 200、TLS 1.3、`sni=encrypted`，实际协议仍为 HTTP/2（h2）：ECH 有连接证据，HTTP/3 未使用，不能外推所有网站。家庭 PAC、Windows DNS、路由器 DNS 与广告过滤继续沿用。[浏览器新连接](../../work/deploy/next/browser-transport-current.txt)、[策略原值](../../work/deploy/next/edge-policy-before.json)、[Microsoft QUIC 策略](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/QuicAllowed)、[Microsoft ECH 策略](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/EncryptedClientHelloEnabled)。

若要固定为显式允许策略，可先保存 Edge 中的工作，在以当前账户提升权限打开的 PowerShell 中执行相邻 [Enable-EdgeTransport.ps1](../../work/deploy/next/Enable-EdgeTransport.ps1)，然后完整退出并重开 Edge，在 `edge://policy` 读回两值，再用真实连接确认协议。脚本尚未成功执行；允许 QUIC 不强制网站采用 H3。若策略影响现有 DNS／PAC 行为，使用 [Restore-EdgeTransport.ps1](../../work/deploy/next/Restore-EdgeTransport.ps1) 按当次快照恢复两项值，不删除其他策略。当前默认已允许协商，此操作属于可选的显式固定。

## 性能与取舍

**2026-10-30 更新：以下三路数字是历史受控批次。当前设备已增加第四路，Ninja 已回滚到路由器，尚未重做同条件四路聚合；不能把 921.67 Mbps 当作当前四路结果，也未验证回滚后的代理路径吞吐。**

境外 DoH 已沿固定香港节点补做候选查询：Windows LAN 通过带认证的路由器 mixed 代理访问 Cloudflare 与 Google，各 3 次均取得 HTTPS 200、证书验证通过及有效 DNS 答案，连接记录确认经过该香港节点。Google、GitHub 与微软下载各域名均通过；DoH 请求计时分别为 67.88～86.85 ms、72.88～85.29 ms，不含代理 CONNECT 与 TLS 握手。这是同一代理路径的短样本可达性，不与此前路由器直连候选作速度排名。当前保留原 Cloudflare fallback，没有将全部生产 DNS 改为境外上游。

浏览器自带 DoH、Android 私人 DNS 和 VPN 可能绕过局域网 53 端口及广告过滤，需按实际终端检查。正常停止 OpenClash 会恢复 dnsmasq 上游；不要在其运行时手工追加一个公共上游，因为 watchdog 会重写该设置。现已启用独立的 `local-health-recovery` 守护：逐个验证本地 53、7874 的 localhost DNS 回答和 1080 的 SOCKS5 协商，每轮完成后等待 60 秒。恰好一个组件连续失败 3 轮，且共享订阅锁内复查仍失败时，才请求对应组件重启。它不根据外网失败触发动作，不切代理节点、不改变 DNS 上游或绕过 UA3F。

守护在启动、PID 变化和恢复请求后等待 120 秒；动作间隔至少 300 秒，滑动 1 小时最多 2 次，当前 `/tmp` 状态生命周期最多 6 次。多个组件同时失败、探针出现未知错误、停用／配置偏离、组件启动或订阅更新占锁时暂停动作。`HEALTHY` 只表示这三个最低本地协议可用，不代表校园认证或互联网正常。路由器上的 10 个 DNS 报文样本、27 个状态／真实锁检查和三个本地协议探针均通过，最终为 `HEALTHY`；没有主动停止生产组件验证实际自动恢复，不能把上述样本写成实机故障恢复保证。

在路由器 SSH 中读取 `cat /tmp/local-health-recovery/status` 查看当前状态；`events.log` 最多保留 128 条恢复事件，仅写内存。`RECOVERY_REQUESTED` 只表示请求已发出，仍需后续探针和真实请求确认。如果需要暂停这项守护，执行 `/etc/init.d/local-health-recovery stop`；需要取消开机启动时再执行 `/etc/init.d/local-health-recovery disable`。这两个命令不修改认证、代理和 DNS 配置。独立 `probe` 会遵守 singleton 锁，已有守护运行时的空输出不能解释为健康。

OpenClash 的普通核心更新入口已受控，避免用公版核心覆盖 Ninja。手动订阅更新事务与容量模块已完成目标 Ruby 语法检查、26 项容量样本、12 项自检及 13 项事务样本；安装后再次通过真实更新入口取得 `OK:UPDATED_VERIFIED`，事务临时目录剩余 0 个，两个校园认证 PID 保持不变。源订阅保留原 49 个节点与原分组；生成配置和运行主组 `🚀 节点选择` 经持久钩子限制为只包含并选择 `香港 02（专线；智能）`；规则仍决定哪些业务使用该组，直连业务保持现有路径。固定香港节点缺失或重复时更新失败，不自动改选其他节点。Ninja 核心仍为 `ab32ad2d`。自动更新保持关闭，没有新增 cron。插件、核心和订阅分别管理；上游包升级可能覆盖更新控制器、核心更新保护、固定节点钩子、容量模块，以及 MWAN、OpenClash、adblock-fast 兼容补丁，升级后必须重新读回并验收。系统未开启固件自动升级。

本地网络当前保留 LAN ULA，但没有公网 IPv6 默认路由；OpenClash 的核心与 DNS IPv6 关闭。这不是完整公网 IPv6 分流方案。三个 WAN 与 LAN 的 MTU 均为 1500，已有双向 TCP MSS 调整规则，没有证据要求进一步降低 MTU。管理 API 配有 secret，代理入口配有认证；WAN 防火墙含管理／代理端口拒绝规则。以上为配置和规则读回，没有做校园 WAN 侧端口实测。

当前已完成受控订阅更新、组件守护、不同账号手机第三通道、九后缀国内 DoH、BBRv1 和双向 CAKE，以及最新成对备份。

CAKE 已在线采用：共享物理 `wan` 入口重定向至 `ifb-cake`，下载 650 Mbit；`wan` 上传 unlimited。两个方向为 `besteffort flows`、`split-gso`、以太网开销、`no-ack-filter`，每个队列内存上限 8 MiB；`codex-cake` 服务运行并启用持久启动，接口 hotplug 与 watcher 按启用状态重建自有队列。三路各自绑定的小 HTTP 请求接收路径均在 IFB 捕获到，不能代替 PC 大下载的外层三路分配证明。此前采用 CAKE 阶段的同源有界开／关样本分别为 263.80／232.81 Mbps，两个 CPU 单核峰值均 94.4%；no-split-gso 样本未全部完成，已恢复 split-gso。整体为 `inconclusive`，未证明稳定吞吐或满载延迟收益，不能把此前 581.55／612.86 Mbps 的差额归因于 CAKE。上传 unlimited 和下载上限偏高仍不能保证控制校园上游队列；没有安装 `sqm-scripts`／LuCI SQM 页面。[队列应用](../../work/deploy/next/cake-applied.json)、[有限对照](../../work/deploy/next/cake-comparison.json)、[三路接收覆盖](../../work/deploy/next/three-queue-coverage.json)。

当前通过已有官方签名索引安装匹配 `6.18.55` ABI 的 IFB、CAKE、BBRv1 三包，永久 repositories 和基础包保持。新建本机 TCP 默认已为 `bbr`，一个实际新建 ESTABLISHED socket 的 `TCP_CONGESTION` 也读回 `bbr`；包内 sysctl 文件提供启动默认。这不追溯切换已有连接，也不证明全部 Ninja／UA3F socket、纯转发 PC TCP 或下载收益。当前是 BBRv1，BBRv3 需独立实现与新内核构建。AccECN 模式 `tcp_ecn=3` 被设备以 EINVAL 拒绝，保持 `2`，无效持久文件已移除；官方同版源码的 sysctl 上限仍为 2，代码符号存在不能替代功能启用。[实际新 socket](../../work/deploy/next/bbr-socket-acceptance.json)、[AccECN 实机拒绝](../../work/deploy/next/accecn-applied.json)、[内核版本边界](../../work/deploy/next/accecn-runtime-boundary.md)。

需要暂停本轮队列时，在路由器 SSH 先执行 `/etc/init.d/codex-cake disable`，再执行 `/etc/init.d/codex-cake stop`，随后读回 `wan`、IFB 与 ingress；它只清理本轮自有队列，不重载网络或认证。BBR 的持久回退另需处理本轮包内 sysctl 文件，只有一次 `sysctl -w net.ipv4.tcp_congestion_control=cubic` 不会取消启动默认。[所有权与精确回退](../../work/deploy/next/adoption-results.md)、[已保存回退脚本](../../docs/local-only-materials.md)。

## 不能上网时

1. 先确认连接路由器 Wi-Fi，并尝试打开管理页。管理页也打不开时，先检查 Wi-Fi、电脑地址和供电，不先刷机。
2. 管理页正常时，读取 `wan`、`wan2`、`wan3`、`wan4` 的地址与 `mwan3 status`。四路共用光猫和物理 WAN，光猫或网线故障会同时影响全部逻辑出口。
3. WAN 有地址但全部逻辑出口均 `offline` 时，检查 ESurfing 认证、DNS 和探测结果。能 ping 通校园网关不足以证明已经认证。启动初期 DNS 尚未就绪时，认证会重试；应区分新进程的 AUTH／心跳与已有通路的在线检查。此前第二通道实例曾自动从在线检查转入新认证并持续保活，但以后排障仍须核对对应 PID；四路 `online` 单独只表示相应出口当前可达。
4. 国内访问正常、国外失败时，检查本机 `ninja-proxy` 与 `127.0.0.1:7890`：先执行 `systemctl --user status ninja-proxy`，再执行 `~/.local/bin/ninja-update status`；路由器已无 OpenClash。手机则检查 Ninja VPN 状态。广告误拦截时，先对具体域名添加白名单，避免整段关闭防火墙或反复重启所有认证。
5. 5 GHz 在启动或无线重载后暂时不可见时，先检查 DFS／CAC 状态，不立即改地区或反复重载。无线已经恢复但性能与基线明显不同时，再检查实际协商宽度、接收队列的 RPS 与 `wireless-steering` 日志；不要直接写自定义 CPU mask。

Windows 上的 ESurfingClient、守护任务、旧完整副本及账号配置已经按授权删除；验证时没有客户端／守护进程及原 8888 监听。旧调试目录中的 5 个历史安装／启动脚本因自动审批拒绝而保留，没有对应活动任务。以后若需要电脑直接认证，须重新安装配置。电脑以太网已恢复 IPv4 DHCP 和自动 DNS，刷机时的 `192.168.31.176` 与 `192.168.1.2` 两个静态地址均已移除；修改前原值已保留，可通过本目录的 `Restore-EthernetDhcp.ps1 -Action Restore` 恢复。当前 Wi-Fi 配置保持不变，仍使用 DHCP。以太网尚未插线，没有取得实际有线租约或验证有线业务；接线后仍需核对地址、DNS 和真实请求。
