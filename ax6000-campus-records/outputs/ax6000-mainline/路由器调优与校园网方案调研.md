## 流量结构与职责

OpenClash 是 LAN 透明代理入口，按规则选择直连、UA3F 或 Ninja。UA3F 只承担选定直连 TCP 的本地代理与明文 HTTP UA 改写；独立 nft TTL 作用于三 WAN IPv4 出口。ESurfing 分别管理三个校园认证；普通 MWAN 随机选择新连接，UA3F 外连使用独立递增轮换。dnsmasq 保留 LAN 53 与 DHCP，广告过滤在入口生效。遵从系统 PAC 的电脑应用在家交给路由器处理。UA-Mask 尚未替换生产 UA3F：其 stock 实现缺少当前 SOCKS5／C9 合同，目标绕过收益不能作为完整 HTTP 改写提速证据；详细比较及接收压力来源见[当前判断](../../work/deploy/wireless-repair/ua-mask-assessment.md)。

```text
LAN 流量 → OpenClash 规则分流
              ├─ 认证／必要校园服务 → 明确 WAN 直连
              ├─ 选定直连 TCP → UA3F 127.0.0.1:1080 → 目的地址
              └─ 远端代理流量 → Ninja → 远端节点

普通真实 WAN 外发连接 → mwan3-nft random → wan、eswan2 或 eswan3
UA3F 新建 TCP（低位 0xc9）→ 独立 ua3f_bal inc → wan、eswan2 或 eswan3
明确 WAN IPv4 出口 → 独立 nft TTL 64

LAN DNS → dnsmasq :53
              ├─ HaGeZi Light 广告域名 → NXDOMAIN
              └─ 其他查询 → OpenClash :7874 → 按国内／校园／境外策略解析
```

UA3F 的 SOCKS5 源码直接拨号到目标地址，选中 UA3F 不会自动在其后串入 Ninja。远端代理使用独立分支，认证和控制流量也保持自己的出口约束。这个结构与上游的 Clash SOCKS 分支接入方式相容，但本机运行结果仍需分别验证。[UA3F 接入说明](https://github.com/SunBK201/UA3F/blob/v3.7.0/docs/zh/guide/proxy-integration.md)、[官方 Clash 分支配置](https://github.com/SunBK201/UA3F/blob/v3.7.0/configs/clash/ua3f-socks5-global.yaml)、[SOCKS5 源码](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/socks5/socks5.go)、[TCP 拨号与 mark](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/base/tcp_linux.go)

## 三路认证与总吞吐的边界

原账号手机／电脑双通道保持，新增另一账号的 Android 手机通道 3。第三 PID 9375 于 21:19:36 完成 AUTH，21:19:44、21:33:55 与 21:48:05 完成三次自然心跳，跨两个完整间隔，声明间隔 850 秒；原 PID 7620／7679 保持，三个绑定出口多轮取得 HTTP 204。MWAN 三成员 online，`balanced` 为 `random mod 3`、`ua3f_bal` 为 `inc mod 3`，各权重 1；已持久设置 `wan3.auto=1`。本轮未重启整机、network 或原认证，冷启动与数日稳定未验证；当前路由器同源短窗聚合收益见性能结果，电脑稳定 900 Mbps 未达到。 源码、维护者与学校资料仍未证明同账号固定仅“电脑一格＋手机一格”；本次另一账号增加第三路成功不能用来推断同账号也可三路。

安装版 `v2.1.5-r6` 与当前主分支的账号加载均按数组动态创建实例，同用户名没有去重，也没有两实例上限或 PC／手机各一个的分类计数。五种 channel 选择 UA、认证报文和相应算法；它们既不能证明五个独立额度，也不能证明服务器只分两类。[固定 HEAD 的账号加载](https://github.com/BadGhost520/ESurfingClient-CVersion/blob/cbc1f8ae2edf60abf66fe991af06698695356c0d/esurfingclient/app/src/config/Config.c#L389)、[channel 映射](https://github.com/BadGhost520/ESurfingClient-CVersion/blob/cbc1f8ae2edf60abf66fe991af06698695356c0d/esurfingclient/app/src/config/ConfigAccounts.c#L16)。维护者在 2026 年 4 月的回复只说明本人使用双 WAN，三 WAN 及以上尚未测试。[维护者原文](https://github.com/BadGhost520/ESurfingClient-CVersion/issues/8#issuecomment-4346972824)。[PR #39](https://github.com/BadGhost520/ESurfingClient-CVersion/pull/39)所称三个 iOS 账号不能改写成同账号三路。

本机第三 Linux、macOS、iOS、Windows 均取得过 AUTH 和首个心跳；Linux 阶段有四轮三源 HTTPS 200，iOS 阶段约 95.6 秒内七轮、共 21 次请求全部为 200。但随后有重新认证，iOS／Windows 加入后主 Android 也重新认证。16:07 曾明确发现两张认证表只剩 unreachable 路由，不能将该段连接失败归为学校限制。所有第三路试验均早于 17:22 的 netifd 原生路由验收；iOS／Windows 声明下次心跳约为 2 小时 59 分，实际观察仅约 1～2 分钟，尚未跨过完整周期。HTTP 302 是客户端检测结果，记录没有给出超过 PC／手机额度的明确服务端原因。详细时间线见 [本机三通道证据复核](../../work/deploy/ninja/three-channel-local-evidence.md)。

广东药科大学的公开指南需要按网络对象区分：[云浮 2023 年指南](http://metc.gdpu.edu.cn/info/1062/1579.htm)规定当时 GDPU 学号账号同时最多两台设备，未分 PC／手机，并列的是旧 8M 套餐；[广州 2023 年指南](http://metc.gdpu.edu.cn/info/1062/1577.htm)没有并发台数与 Mbps；[中山 2026 年指南](http://metc.gdpu.edu.cn/info/1062/1673.htm)描述学校自建全光纤、全 WiFi，当前默认联通，也没有当前天翼账号的额度。用户已确认位于中山校区；上述中山指南中的学校自建网络不能直接替代本账号的电信套餐规则。用户的套餐未标明 Mbps，当前公开证据不足以确认其限速值。

另有经源码核对、可列入试验的旧 Android 协议候选。[EchoPing07/Esurfing-go-webui 的固定 README](https://github.com/EchoPing07/Esurfing-go-webui/blob/2b5309d2f93b2b0889693ff96b52f37a201aa55a/README.md)区分 PC、新 Android `2104` 和旧 Android `2089`／`2093`，作者报告三种协议分别通过真实认证，但没有明确交代同账号三路同时共存的学校、时间与心跳证据，且项目已声明停止维护。当前 CVersion 的 Android 选项仅采用 `2104`，旧 UA 常量没有被配置路径使用，旧算法分派也已注释，不能在 LuCI 复制一项就得到这条候选路径。[CVersion 旧算法分派](https://github.com/BadGhost520/ESurfingClient-CVersion/blob/cbc1f8ae2edf60abf66fe991af06698695356c0d/esurfingclient/app/src/cipher/CipherFactory.c#L19)。候选源码有九种旧代算法的实际注册与加解密调用，按接口保存会话并恢复原 UA；Linux 绑定设备失败时会降级为只绑源 IP，复试仍需读回真实出口。详见 [旧 Android 候选核对](../../work/research/old-android-candidate.md)。该历史核查没有安装旧 Android 候选；本轮新增的是不同账号的现有 Android 通道。

**三路聚合对路由器多连接下载已证明有用，电脑稳定 900 Mbps 尚未达到。** 临时关闭自有 CAKE 后，固定同一微软 URL、实际 IPv4 `171.108.211.12`、总计 12 条连接与完整 768 MiB，单／双／三／再单为 330.89／611.24／921.67／348.43 Mbps。每条本机请求均以 PID、socket inode 与 conntrack 核对出口；实际分配为 12／0／0、6／6／0、4／4／4、12／0／0。三路比双路增加约 50.8%，比前后单路平均约为 2.71 倍。921.67 Mbps 是完整批次 6.99 秒均值；它没有经过电脑完整路径，不能称为稳定 900 Mbps。[本轮结果](../../work/deploy/aggregation/result-summary.json)、[受控单／双／三／单](../../work/deploy/aggregation/controlled-cases.json)。

固定相同数字目标经本机 `127.0.0.1:1080` UA3F SOCKS5 下载，12 条请求完整完成 768 MiB，7.14 秒、902.30 Mbps；捕获 12 条新增 UA3F Internet socket，三路各 4 条且都有正文接收增长。随后裸三路相同批次为 7.09 秒、908.67 Mbps，每条出口核对通过。UA3F 组 CPU 平均 57.5%、单核采样最高 77.0%；裸重复组平均 33.7%、最高 52.5%。这说明选定端点和这些短窗下，UA3F 本机路径也接近千兆，不能把电脑低速笼统归为 UA3F 固定上限；本机 SOCKS 测试没有经过 OpenClash、电脑 Wi-Fi 或完整额外 TCP 链。[同端点分层](../../work/deploy/aggregation/ua3f-layer-cases.json)。

当前电脑经 Wi-Fi → OpenClash → UA3F 的五个完整 768 MiB 批次为 162.44／169.60／352.73／254.92／213.50 Mbps，均未接近 900 Mbps。电脑 `--resolve` 只固定内层连接，代理重建后实际 CDN 会变化；最新批次捕获到 `120.226.112.10` 的 7 条新增 UA3F 外连，按出口为 3／3／1，三路同窗均有大量正文增长，未逐条映射全部 12 条电脑请求。352.73 Mbps 批次 CPU2 平均 busy 96.4%、softirq 89.9%，说明完整路径有处理压力候选，尚不能确定某程序或某参数为唯一原因。另一固定 CDN `111.2.112.12` 的裸三路只有 146.25 Mbps，CPU 明显有余量；来源／路径也会限制吞吐。两次 CAKE 开／关 PC 对照的实际 CDN 未固定且方向不一致，不能判定 CAKE 提速或降速。[电脑实际外连](../../work/deploy/aggregation/pc-actual-cases.json)、[另一固定 CDN](../../work/deploy/aggregation/endpoint-controlled-cases.json)。

电脑必须继续使用 Wi-Fi。现有证据不支持将电脑低速直接判为学校检测到共享后限速；实际 CDN／到目标的路径不同已确认影响对照，完整电脑路径在部分批次存在明显单核／softirq 压力。保持 UA3F、出口 TTL64 和现有卸载基线的本机路径已达 902.30 Mbps，因此没有“防检测一开就普遍限到两三百 Mbps”的证据。不过本机测试没有无线发送及 OpenClash 入站，不能排除为了保留防检测而采用的软件代理链、额外 TCP 段及关闭 WED 与无线处理竞争产生本地成本。UA3F 的 HTTP UA 改写处理请求，TTL64 由独立内核规则处理；不能把全部下载正文描述为逐包改 UA。无线本身、OpenClash、UA3F 和关闭卸载各自损失多少仍未分离。[防检测分层分析](../../work/deploy/aggregation/wireless-antidetection-analysis.md)、[CPU／重传／无线样本重算](../../work/deploy/aggregation/wireless-sample-analysis.md)。

从 16 增至 32 并发时，观察值只再增加约 2.95%，CPU 平均值却由约 58.1% 增至约 70.0%。这仅描述这两批数据，足以说明不能把无限加线程当作优化。32 路样本的 WAN 计数约为主 673 MB、第二 619 MB，超过约 1074 MB 的有效载荷；计数口径、背景流量和额外字节来源尚未确认，不直接称为重传。CPU 未满也不能代替每核、softirq、队列和满载延迟分析。对 conntrack 采样排除测试开始前已有项后，16／32 个新外层连接分别为 8:8／16:16，8 连接批次仍为 4:4。

后续相同 16 × 64 MiB 的计数检查记录到 TCP 内存压力、乱序队列丢弃和裁剪。实际页大小从进程 auxiliary vector 读回为 4 KiB；原始 `tcp_mem=5727 7638 11454` 对应约 22.37／29.84／44.74 MiB 的全局阈值。仅把该运行值临时改为 `8192 16384 24576`（32／64／96 MiB），其他参数不变，完成候选后恢复原值。原值→候选→原值三次完整 1 GiB 平均为 547.69→470.74→547.30 Mbps。候选的 `TCPMemoryPressures` 增量从 16 降为 1、`TCPOFODrop` 从 1,972 降为 30，但累计压力时长为 330／320 ms，下载没有变快；候选抽样 TCP 内存峰值约 49.93 MiB、`MemAvailable` 最低约 122.75 MiB。计数包含后台流量，低频采样也会漏瞬态，不能据此推断单一损失位置或长期内存安全。候选未持久化，不增加 backlog、每 socket 缓冲或其他内核参数。[Linux TCP 内存参数](https://github.com/torvalds/linux/blob/v6.18/Documentation/networking/ip-sysctl.rst)、[压力计数实现](https://github.com/torvalds/linux/blob/v6.18/net/ipv4/tcp.c)

此前 USTC／TUNA 混合批次的单路 76.81／79.42 Mbps、双路 148.92 Mbps 主要用于早期受限比较；随后 USTC 同源批次因 HTTP 429 未完成，其 `observed_Mbps` 无效。该历史阶段总吞吐结论以完整的微软同源批次为准；当前三路采用前述固定总并发对照，保留这些失败限制，避免把未完成传输当作吞吐。32 MiB 在 700 Mbps 下约 0.38 秒即传完，亚秒请求的握手和慢启动占比很高；短 Range 更适合定位路径，不适合宣称持续容量。

一次普通 TCP 或 QUIC 连接通常仍使用一个出口。多 WAN 的按连接分配可改善多连接总负载分布，不会自动把一条连接的速率相加；同一物理千兆 WAN 也限制全部外发总量。Ninja 如果复用多个应用到少量外层连接，mwan3-nft 看到的是外层连接，实际分配必须观察这些连接。[mwan3-nft 说明](https://openwrt.org/docs/guide-user/network/wan/multiwan/mwan3-nft)、[Mihomo 代理公共字段](https://wiki.metacubex.one/config/proxies/)、[MPTCP FAQ](https://www.mptcp.dev/faq.html)

当前没有引入需要远端配合的 MPTCP 或多路径隧道，也没有证明需要这类附加服务。它们会增加服务器、封装和维护成本，不作为当前三出口配置的隐含能力。[OpenMPTCProuter](https://github.com/Ysurac/openmptcprouter)

## mwan3-nft、认证与代理标记

本机采用社区移植的 `mwan3-nft 3.6.12-1`。原默认掩码 `0x3f00` 与代理标记共用位，已经改为 `0x3f000000`。实现同时处理了本机代理接管、本地认证进程和代理重新发出的连接，不能把实际修改简化为只换一个 mask。[mwan3-nft 发布](https://github.com/dl12345/mwan3/releases/tag/v3.6.12-1)、[掩码实现](https://github.com/dl12345/mwan3/blob/cdd4fc56f4de9ccf56d40d6dc04a5b6a4e5a0ae6/files/lib/mwan3/common.sh)、[路由与 hook](https://github.com/dl12345/mwan3/blob/cdd4fc56f4de9ccf56d40d6dc04a5b6a4e5a0ae6/files/lib/mwan3/mwan3.sh)

| 处理对象 | 当前安排 | 需要保持的契约 |
| --- | --- | --- |
| WAN 分类 | 高位 mask `0x3f000000` | 不覆盖或误解释 OpenClash 的低位接管值 |
| 主 ESurfing | GID `65201`，default sentinel | 主会话的认证与心跳固定主出口 |
| 第二 ESurfing | GID `65202`，完整 mark `0x02000000`，table `25202` | netifd DHCP 变化后更新对应路由，不借用主出口认证 |
| OpenClash UDP 接管 | 低位 `0x162` 与 mwan 高位隔离 | 送往本机核心的包先满足本地代理路由；真实外发连接再选择 WAN |
| 本地代理路由 | 优先级 `100` 的 masked route | 高位出口值变化不会破坏低位本地接管匹配 |
| UA3F | 只用本机 SOCKS；低位 `0xc9` 的新 TCP 进入专用 `ua3f_bal`；自动 TPROXY／REDIRECT／HTTP NFQUEUE 关闭 | 先恢复 CT 和处理内网绕过，再分配；setter 和 CT 仅修改高位 WAN mask |
| DNS 53 | default 规则先于 balance | DNS 的必要出口选择不被普通分配改变 |

OpenClash 原始实现使用 `0x162`，部分分支按完整值匹配；若只在该值上叠加高位 WAN mark，原匹配仍可能失败。本机已经按接管与真实 OUTPUT 两阶段处理，并通过 UDP 请求和重载验证。上游源码仍是复查升级兼容性的依据。[OpenClash init](https://github.com/vernesong/OpenClash/blob/e553e82e01c697aefbe1555261a503f425e00ccd/luci-app-openclash/root/etc/init.d/openclash)

UA3F TCP 出站使用 `0xc9`，自动 TPROXY 路径另有 `0x1c9`；原 HTTP NFQUEUE 中还存在完整覆写 conntrack mark 的分支。当前 SOCKS 配置不启用这些全局接管和 HTTP 队列功能，不能从高位 mask 已调整推断它们可以任意打开。[UA3F NFQUEUE verdict](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/nfqueue/nfqueue_linux.go)

普通连接分配保持 `numgen random`。原来 LAN 分类与 UA3F 外层共用递增序列，成对连接会消耗相邻序号并使外层固定偏向一侧；不能恢复这条共享计数器的全局 inc。早期 16 个新百度 HTTPS 请求全部为 200，主出口 5 个、第二出口 11 个，只能证明两路都参加了成功请求。

UA3F 的实际外发 TCP 使用独立 `ua3f_bal`：当前三个 IPv4 member 同 metric、weight 为 1，`numgen inc mod 3` 与 LAN 的 random 分开。跳转在 OUTPUT 的 CT 恢复与 connected 绕过后、普通规则前，匹配高位 WAN mask 为 0、低 24 位为 `0xc9`，赋值和 CT 保留低位。此前双路 mod 2 的微软批次捕获 8 条外层连接按 4:4 分配；该历史验收不作为当前三路大下载分配证明。

Linux 为每个 numgen expression 分配独立原子计数器；专用 policy 不由 LAN 分类消耗。它轮换新连接，背景请求、重试、policy 重建与各连接完成量仍会改变特定批次的比例。offline 成员从生成政策中移除；全部 offline 使用 last_resort unreachable。新增第三路 hotplug 跳过全局 conntrack 清理，保留现有连接；既有 TCP 仍不能更改源地址后无缝迁移。[Linux numgen](https://github.com/torvalds/linux/blob/v6.18/net/netfilter/nft_numgen.c)、[nft 负载分配](https://wiki.nftables.org/wiki-nftables/index.php/Load_balancing)。

mwan3-nft 规则名保持不超过 15 个字符，DNS 53 的 default 规则排在 balance 之前。这些限制属于现有实现契约，后续改规则和升级时仍须核对实际生成的 nft 结构及对应路由。

## WAN 健康检查

健康检查使用自定义 `curl204`，严格要求 HTTP 204；小米／华为探测沿各自出口运行。原双路探测与新增第三路的独立 204 已通过；MWAN 三路均 online。ping 校园网关、HTTP 200、认证重定向或借用另一出口成功均不计当前出口通过。

状态初始为 offline，只有真实探测结果才能让接口进入可用状态。`down=3`、`up=3` 沿用现有 score 累加和滞后机制，不能解释成“连续三次失败才下线”或“连续三次成功就恢复”。判断故障和恢复时应读取 score、当前状态与实际探针出口，而不是仅数日志行。

最新软件重启后再次临时丢弃第二 WAN 的健康探针：约 44 秒进入 offline，普通 `balanced` 和专用 `ua3f_bal` 均只保留主出口，国内新请求为 200。第一次 Ninja 请求超时，重复实验在约 44.3 秒 offline 后的 gstatic 请求为 204，未重置代理 API；解除阻断后，该次实验总计约 59.0 秒恢复 online，并再次取得 204。首次超时的原因未确认，不能把重复成功写成无缝迁移。此前组合的对照为约 39.1 秒 offline、解除后约 17.5 秒恢复；时间受 score 和探测时点影响，不用两次差值作性能结论。

实验验证当前探针、score 与新连接的选择路径；一次代理请求超时不构成需要自动重启核心的证据，也没有确定它是否复用了此前的底层连接。没有拔网线、终止认证或模拟长时间物理断网，共享网线和上游设备故障可同时影响全部逻辑出口。

## UA3F 当前能力与退役的 TC TTL 路径

UA3F `3.7.0` 的本地 SOCKS5 监听为 `127.0.0.1:1080`，显式经过本机 SOCKS5 的明文 HTTP 请求已观测到 UA 为 `FFF`，HTTPS 请求正常转发；普通 LAN 的 HTTP 检测保留测试 UA，因此不能把该结论扩展到所有 HTTP。SOCKS 服务只开放回环，未启用 HTTPS MitM、Desync、Inject、全局 UDP/443 阻断、IPID、TCP Timestamp、SYN Window 或 L3 BPF。相应上游 TCP 由路由器栈重新建立，但 TLS 握手字节继续转发，HTTPS 内层 UA 不被改写；普通 NAT、UDP 和未进入该分支的 TCP 不因此统一。HTTP UA 的统一不等于 TLS ClientHello 的可见部分、其他请求字段、连接数和时序都被统一。[TLS／HTTP 分支](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/base/server.go)、[MitM 限制](https://github.com/SunBK201/UA3F/blob/v3.7.0/docs/zh/http-rewrite/mitm.md)

当前 SOCKS5 路径没有跨客户端共享的 HTTP 上游连接池。`socks5.handleConnect` 每收到一条 CONNECT，就通过 `base.Connect` 新建 TCP，固定赋给该连接的 `RConn`；HTTP 改写后执行 `Request.Write(c.RConn)`。同一下游 TCP 内可以保持 HTTP keep-alive，但不同下游 TCP 不会因目的 URL 相同而合并。非 HTTP `Cache` 只是嗅探跳过集合，`BufioReaderPool` 只复用缓冲。存在 Go `DefaultTransport.RoundTrip` 连接池的是 `server-mode=HTTP` 的普通非 CONNECT 分支，不能套到当前 SOCKS5。[SOCKS5 handleConnect](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/socks5/socks5.go#L213)、[TCP 新建](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/base/tcp_linux.go#L17)、[HTTP 写入固定连接](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/base/server.go#L270)、[另一 HTTP 服务路径](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/http/http.go#L122)

下载任务数仍不等于 TCP 连接数。若需要排除客户端复用，可让每个请求使用独立 curl 进程、`--http1.1` 和 `Connection: close`，再数实际外层连接。`curl --no-keepalive` 只停 TCP 保活探针，不是 HTTP 禁复用选项。[curl 定义](https://github.com/curl/curl/blob/master/docs/cmdline-opts/no-keepalive.md)

本机曾在开启 TTL eBPF 后发生 WiFi 无网回归，用户随后手动断电。源码复查找到 `parse_l2` 的具体错误：它在读取 Ethernet 头之前，只按首字节判断裸 IPv4。目的 MAC `48:46:fb:f7:c4:c9` 的 `0x48` 会被解释为 IPv4 version 4、IHL 8，导致 L3 offset 错误成为 0。[TC 程序](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/bpf/tc/tc.c)

`set_ip_ttl` 随后把帧 offset 8 当 TTL、offset 10 当 IPv4 checksum。实际这几个字节属于 Ethernet 源 MAC，真实 IPv4 TTL 位于 offset 22。使用未改动的正式标签 C 函数体和 host helper shim，本机离线构造帧复现了以下结果；这次复现没有执行路由器 ARM64 程序或内核 BPF。

| 复现输入源 MAC | host replay 输出源 MAC | 真实 IPv4 TTL |
| --- | --- | --- |
| 主 WAN `4c:c6:4c:2c:2e:65` | `4c:c6:40:2c:3a:65` | 37 保持为 37 |
| 当时 eswan2 `02:66:60:00:00:02` | `02:66:40:00:20:02` | 37 保持为 37 |
| 当时 eswan3 `02:66:60:00:00:03` | `02:66:40:00:20:03` | 37 保持为 37 |

普通目的 MAC 控制组则保留源 MAC，并将真实 TTL 37 改为 64。实机网关 MAC、源 MAC 条件和当时 TCX 附件与缺陷触发条件相符，因此该源码错误高度相关。当前没有在线捕获当时被破坏的帧，也没有内核崩溃证据，不能断言它是整次回归的唯一原因。

此外，UA3F 会先启动 L3 helper，再启动主 SOCKS server；verifier、接口枚举或 attach 失败可使整个进程退出，从而影响依赖 `127.0.0.1:1080` 的流量。单纯“代理端口消失”和“包头被改坏”需要分别判断。[服务启动顺序](https://github.com/SunBK201/UA3F/blob/v3.7.0/cmd/root.go)、[TC 出口选择](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/bpf/tc/tc.go)

当前保持 UA3F 的全部 L3／BPF 关闭，原 TC 自动重挂方案停止使用。classic fallback 仍使用同一个程序，不能作为回避该缺陷的办法。独立 nft TTL 路径也不依赖 UA3F 的默认路由枚举或 TCX ifindex。

通用 `bpf-offload` 是另一个 socket sockmap 路径，使用成对 TCP socket 的 `SOCKHASH`／`sk_skb`，与 TC TTL 的 `l3-rewrite.bpf-offload` 不同，不调用 `parse_l2`。但当前没有证据支持直接启用：stock init 未导入这个开关，且 v3.7.0 `TryOffload` 注释、调用方继续 copy 的行为和连接生命周期还需运行验证。已有 CPU 未满的观察也没有建立“UA3F 饱和”前提。这个选项只保留为具体瓶颈成立后的候选，未运行、未承诺收益。[sockmap 加载](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/bpf/sockmap/sockmap_linux.go)、[TryOffload](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/base/server_linux.go)、[stock init](https://github.com/SunBK201/UA3F/blob/v3.7.0/openwrt/files/ua3f.init)

## 独立 nft TTL 64

当前 nft TTL 规则匹配明确 Linux 出口 `wan`／`eswan2`／`eswan3`，将 IPv4 TTL≥10 的外发报文设为 64，保留低 TTL 探测语义。此前双路阶段的实际探针原 TTL 为 37，出口抓包观察到 64，Ethernet 源 MAC 保持原值；该抓包结论不外推第三路已完成相同报文实验。新增第三路只增加对应出口规则，没有重新启用 eBPF。

此处设置 64：IPv4 转发减 1 已在 postrouting 之前发生。65 适用于 LAN ingress 设置后还要转发减 1 的补偿，当前规则没有加入这种 ingress 路径。stock UA3F 的非 BPF TTL helper 范围更大，不能只将 BPF 关掉、TTL 保持开启后直接视为同一部署。[UA3F TTL 文档](https://github.com/SunBK201/UA3F/blob/v3.7.0/docs/zh/l3/ttl.md)

出口规则和真实抓包都只支持对应 IPv4 路径。软件／硬件 flowtable 可以绕过部分常规 Netfilter 处理，长期 LAN 转发流、加速设置变化、IPv6 Hop Limit 和其他隧道仍须分别验证。不要根据路由器本机 ICMP 的 37→64 结果推断每一种流量均被覆盖。[Linux flowtable](https://docs.kernel.org/6.18/networking/nf_flowtable.html)

TTL64 只统一一个字段，不会让三套 DHCP 租约和认证会话变成一个身份。学校实际检测机制没有确认，不能承诺校园识别不会触发。

本地 UA3F 让经过它的上游 TCP 来自路由器栈，普通 NAT／UDP／绕过流量仍保留各自特征。MitM 关闭时，客户端 TLS ClientHello 的可见部分不被统一；HTTPS 内的 HTTP Header 本来由 TLS 保护。远端隧道可以隐藏确实进入其中的内层内容，但外层目的地、协议、总量和时序仍在。无论采用哪条分支，都没有不可识别的证明。[TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html)、[UA3F 转发源码](https://github.com/SunBK201/UA3F/blob/v3.7.0/internal/server/base/server.go)

`udp:false` 只限制当前 UA3F SOCKS 节点，并不等于全局没有 UDP/443。若实际抓包确认某个浏览器绕过 TCP 链，可对单个客户端、互联网出口和 UDP/443 做短时 reject 对照，再检查 TCP 回落、延迟和功能。不要全局封 UDP；UDP/443 还可能承载远端隧道，其他端口也可能使用 QUIC。当前没有执行该对照。[HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html)、[UA3F UDP/443 阻断说明](https://github.com/SunBK201/UA3F/blob/v3.7.0/docs/zh/l3/block-quic.md)

Linux 默认 Timestamp 每连接加入随机偏移，因此不同连接的 TSval 不同正常，NTP 校时不会移除它。Timestamp 用于 RTT 和 PAWS，IPID 与非原子数据报的分片重组有关；不依据教程一次清除全部字段。旧 rkp-ipid 上游已归档，增加模块还须匹配精确内核 ABI。UA2F 的正确上游是 Zxilly，正式 `v5.2.0` 已有 NFQUEUE／REDIRECT／TPROXY；旧文章的“只有队列”说法过时，但当前没有与 UA3F 叠装的必要，也没有其本机性能对照。[Linux 6.18 Timestamp 参数](https://github.com/torvalds/linux/blob/v6.18/Documentation/networking/ip-sysctl.rst)、[RFC 7323](https://www.rfc-editor.org/rfc/rfc7323.html)、[RFC 6864](https://www.rfc-editor.org/rfc/rfc6864.html)、[UA2F v5.2.0](https://github.com/Zxilly/UA2F/blob/v5.2.0/README.md)、[rkp-ipid](https://github.com/CHN-beta/rkp-ipid)

## 电脑与 Android 的家庭／外出切换

电脑为 Clash Verge `2.5.2`，Ninja 核心 `ab32ad2d`，TUN 关闭。系统 `ProxyEnable=0` 表示手动代理关闭，但 `AutoConfigURL` 指向回环 PAC `127.0.0.1:33331/commands/pac`，遵从系统 PAC 的应用仍会求值。现在的家庭条件为：本机 IPv4 属于 `192.168.31.1～254`，并且 `ax6000-home31.lan` 解析到 `192.168.31.1`；二者同时满足时返回 `DIRECT`，交给家庭路由器分流。其他状态保留原 PAC。

实际 PAC handler、磁盘内容和候选已逐字核对；Windows 原生求值中，微软下载、Steam CDN／商店／社区、百度、GitHub、Google 共 7 个域名均为 `DIRECT`。核心、14 组名称与类型、Selector 选择、3,528 条规则和用户级环境代理保持原值，11 项运行验收通过。另有 288 个脚本断言覆盖家庭／其他网段、边界、IPv6、回环和 DNS 标识缺失；它证明脚本行为，不替代真实外出切换。[Windows PAC 求值接口](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpgetproxyforurl)、[PAC 实现差异](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Proxy_servers_and_tunneling/Proxy_Auto-Configuration_PAC_file)

家庭 DNS 标识用于减少相同网段的误判断，不是认证协议。多网卡、IPv6、程序自带 DoH、缺少标识或求值异常时可能保留本机代理；运行应用也可能缓存旧 PAC。固定应用代理和 CLI 的 `HTTP_PROXY`／`HTTPS_PROXY=127.0.0.1:7897` 不随 PAC 切换，当前保留用户级环境以支持外出使用。单次 CLI 候选已验证调用期间移除或恢复代理变量、结束后精确还原，但没有部署长期的全应用切换。[Clash Verge PAC handler](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.2/src-tauri/src/utils/server.rs)

## 存储方案与未采用路线

当前整套在 stock 布局落盘并运行，暂不需要改引导器。先前清理 GeoSite 和未引用 provider 后，overlay 可用约 14.3 MiB；最终验收读回约 13.6 MiB，余量会变化。这是减少重复或未使用数据的结果，不是扩大分区。已安装的手动订阅容量检查默认保留 overlay 4 MiB、`/tmp` 32 MiB、MemAvailable 64 MiB；下载前与发布前分别读回，再计入候选、投影、备份和回滚工作空间。发布需求按 `2S + 2G + C + P + 64 KiB + 4 MiB` 计算，文件向上取整到 4 KiB；`S`、`G` 是旧源与旧生成，`C` 是新源，`P` 为投影的两倍加 256 KiB，原有备份不计作可回收空间。当前尺寸演算需约 6.04 MiB overlay，下载前需 44 MiB 临时空间、约 107.9 MiB 可用内存。它不预留资源，也不保证检查后其他进程不会占用空间；失败仍依赖事务拒绝或回滚。核心升级另行计算旧核心、备份、新下载和回滚峰值。当前余量不足以直接部署逻辑安装量约 32.55 MiB 的 AdGuard Home。系统日志为设置 128 KiB 的内存缓存；OpenClash 日志在 `/tmp`，watchdog 按 512 KiB 设置周期清理，检查之间可能超过该值。没有新增日志轮转任务或闪存日志。

## 本地业务故障守护

已部署 `/usr/libexec/local-health-recovery`、Lua 5.1／nixio 探针和独立 procd init，已启用并读回 `HEALTHY`。探针对 127.0.0.1:53 和 :7874 发 localhost IN A，验证源端口、事务 ID、问题、rcode 与回环 A 记录；1080 只验证 SOCKS5 方法协商，处理 TCP 短读并有 5 秒总截止。它不查询公网，所以校园断网、远端 DNS 或香港节点故障不会直接触发重启。

恰好一个组件连续失败 3 轮，且共享订阅锁内再次核对配置、PID、init 状态和三个探针后仍失败，才局部请求重启。每轮后等待 60 秒；启动、PID＋starttime 变化和动作后宽限 120 秒，动作间隔至少 300 秒，每滑动小时最多 2 次、当前内存状态生命周期最多 6 次。失败的恢复请求也扣预算；组件停用、未知探针、组合失败、订阅锁或核心更新会暂停动作。状态与最多 128 条事件仅存 `/tmp`，没有 cron 或闪存轮转。

路由器上通过 10 个 DNS 报文样本、27 个状态／真实 flock 样本以及三个现场协议探针，安装不改变业务 PID；最终状态为 `HEALTHY` 且无恢复事件。尚未通过主动挂起或停止生产服务验证实际自动恢复。`RECOVERY_REQUESTED` 只表示 init 请求返回，不能替代新进程、后续探针及真实应用验收。参见 [目标验证](../../work/deploy/router-local-health-validation.json)、[安装读回](../../work/deploy/router-local-health-installed.json) 和 [本轮最终业务结果](../../work/deploy/router-optimization-final.json)。

## 本地网络、管理入口与完善顺序

21:32 读回 WAN、第二 WAN 和 br-lan 的 MTU 均为 1500，fw4 已有 ingress／egress 的 TCP SYN MSS clamp，按 `rt mtu` 取值。这不覆盖 UDP／QUIC，也不证明全部目的路径的 PMTU，但目前没有证据要求无差别改成更低 MTU。历史默认 AQL 的 LAN 下行样本约为 869 Mbps～886 Mbps，旧双路完整校园路径约为 462 Mbps～613 Mbps。当前 LAN 为 567.06 Mbps～605.33 Mbps，电脑完整三路路径为 162.44 Mbps～352.73 Mbps；这些包含不同来源、时间与处理路径，不能唯一定位公网瓶颈，当前 900 Mbps 目标以三路聚合实测段落为准。

电脑当前 WLAN 使用 DHCP，上网正常。Ethernet 已恢复 IPv4 DHCP 和自动 DNS，刷机时的 `192.168.31.176` 与 `192.168.1.2` 两个静态地址已移除；原值已保存，本目录 [Restore-EthernetDhcp.ps1](Restore-EthernetDhcp.ps1) 提供恢复入口。Wi-Fi 配置保持不变。以太网仍未插线，尚未取得实际有线租约或验证有线流量，不能把配置读回当作有线应用验收。脚本初次读回因断开网卡短暂没有 IPv4 地址报错，后续独立读回确认 DHCP、自动 DNS 和静态地址清理已生效，脚本也已允许无地址状态。[以太网配置验收](../../work/deploy/ethernet-router-optimization.json)

UA3F 只监听回环。OpenClash controller 监听所有接口的 9090，但已有 secret，mixed 代理也有认证；WAN input 存在 reject，OpenClash WAN input 明确拒绝 7874／7890／7891／7892／7893／7895／9090。SSH、LuCI 的所有接口监听不能直接等同校园 WAN 可达。此处读回了规则与认证状态，没有外网端口扫描；若未来改防火墙或对外暴露服务，应再核对实际入口。

当前已完成受控订阅更新、固定 Ninja／香港 02、本地组件守护、另一账号手机第三通道、九后缀国内 DoH、BBRv1 和双向 CAKE。配置、最新成对备份及 E 盘另一物理磁盘隔离展开均有对应摘要。加密和队列采用没有证明公网稳定提速，校园 gdpu 样本失败仍保留；长期运行、主动故障恢复、有线应用、外出与真实灾难恢复尚未验证。

## 未启用能力与仍未完成的验证

当前没有启用全网 MitM、Desync／TCP Inject、全局 UDP/443 阻断、UA3F TC IPID／Timestamp／SYN Window 或其他重复全局接管工具。IPID 与 Timestamp 有协议语义，不能为“统一指纹”随意移除；UDP/443 阻断也不保证应用回退到 TCP。[IPv4 ID 语义](https://www.rfc-editor.org/rfc/rfc6864.html)、[Timestamp 标准](https://www.rfc-editor.org/rfc/rfc7323.html)、[QUIC 阻断说明](https://github.com/SunBK201/UA3F/blob/v3.7.0/docs/zh/l3/block-quic.md)

最新读回没有 IPv6 公网默认路由：`wan` 只有 link-local，`eswan2` 没有 IPv6 地址，LAN 保留 ULA。这是当前网络状态，不是完整 IPv6 分流方案。UA3F v3.7.0 TC 源码及当前 nft TTL 都只处理 IPv4；以后获得公网 IPv6 默认路由时，要另验 DNS、LAN、透明代理和 Hop Limit 覆盖。

仍未证明的范围包括 Watchdog 早期退出根因、第三路与新队列冷启动、硬断电和数日三路运行、重复续租／重连、真实外出 PAC／Android 自动切换、Edge 下载分叉、固定账号配额与电脑稳定 900 Mbps、上传和远端代理满载延迟、HTTP/3 完整业务、生产故障恢复与真实灾难恢复。三路自然心跳、独立可达、策略接入、各自小请求的 IFB 接收覆盖及一个 BBR 新 socket 已通过；当前本机固定源三路 12 条大下载外连已捕获，电脑最新批次有三路同窗正文增长；电脑逐请求映射、长期收益与稳定 900 Mbps 仍缺。

Edge 155 当前没有 `QuicAllowed`／`EncryptedClientHelloEnabled` 禁用策略，未设置时默认允许相应协商。本轮尝试将当前用户两项策略明确写为 1，Windows 拒绝创建 HKCU 策略分支，实际没有新增策略。指定 `crypto.cloudflare.com` 新连接取得 HTTP 200、TLS 1.3、`sni=encrypted`，实际协议仍为 HTTP/2（h2）：ECH 有连接证据，HTTP/3 未使用，不能外推所有网站。家庭 PAC、Windows DNS、路由器 DNS 与广告过滤继续沿用。[浏览器新连接](../../work/deploy/next/browser-transport-current.txt)、[策略原值](../../work/deploy/next/edge-policy-before.json)、[Microsoft QUIC 策略](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/QuicAllowed)、[Microsoft ECH 策略](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/EncryptedClientHelloEnabled)。

DoH3／DoQ 沿固定香港路径仍未取得成功业务，L4S／DualPI2 与 MPTCP 未采用。精确 ABI 有 DualPI2 部署入口，但没有真实 ECT(1)、可扩展拥塞控制、CE／反馈与混合流量证据；不能把 CAKE 或普通 ECN 当作 L4S，也不能把 DualPI2 加作 CAKE 子队列。Kuma、Tailscale、collectd 继续按选择不安装。ImageBuilder 已完成 stock、包／ABI 和本地补丁分层准备，未构建或刷机。[五项机制当前结果](../../work/deploy/next/adoption-results.md)、[ImageBuilder 维护准备](../../work/deploy/frontier/imagebuilder-readiness.md)。
